## Mode: skills

### Domain table

Optional keys inside a domain entry (`key: value`, read by the pipeline template): `mode:` mode file under the skill's `modes/` that the fixture contract loads with SKILL.md; `scale_chars: high=<H>,extreme=<E>` overrides the size floors; `haystack:` the candidate pool high/extreme problems must carry; `template_sections_not_fp:` output sections whose extra entries are not false positives; `sev_label:` the output label severity accuracy reads; `real_fixtures:` repo-relative directory of frozen real problems, attached on `--full` when present; `fetch_store:` repo-relative directory holding, per real problem, the frozen results of the lookups the skill would make live (`<problem_id>.json`, keyed by item number), which the solver reads in place of the fetch so a verdict can rest on verified evidence; `derived_gt: true` ground truth is computed from the fixture by a deterministic tool rather than copied from `input`, so Phase 1b skips the token-occurrence check (`--derived-gt`); `open_shape: true` synthetic problems are shaped like real reports — candidate rows with short snippets, no code in the pool, no copied phrase between item and answer (`--open-shape`); `boundary: true` high/extreme problems must hold ≥ 3 answers one step from a different outcome, checked on the saved derived outputs (`--boundary`); `weak_probe: off` skips the Phase 1c weak-solver probe for a rubric-bound domain; `verdict_tier: real` takes the calibration verdict from the real tier, synthetic aggregates still reported; `solver_model: <tier>` runs the Phase 2 target at the tier the skill itself dispatches that step at, overriding frontmatter, so recall is measured at the shipped tier; `precision_gate: per-role` ground-truth items sharing one `role` form a group, and a response naming anything in that role that no item of the group carries voids the group (its items count as not found) — every scorer of the domain applies it, the Phase 1c probe included, so naming every candidate never scores. An entry runs under its own backticked name as label (`/oss:analyse`, `/oss:analyse vitality`); its run slug strips the leading `/` and replaces `:`, `/` and spaces with `-` (`oss-analyse`, `oss-analyse-vitality`), per SKILL.md Step 1; `mode:` selects the mode file only.

Skill domains:

- `/foundry:audit` → synthetic `.claude/` config with N injected structural issues. **Focus on cross-file JUDGMENT issues** (tool-grant mismatch, inter-file contract split, dead dispatch path) — mechanical/deterministic classes (fence, tag, README/version drift, mode-dispatch, bash-persistence, orphaned-bin) already recall-benchmarked at 100% by `plugins/cc_foundry/tests/audit/test_audit_static.py` (Step-1b Layer-1 driver), so injecting those adds no signal; inject defects a per-file pass would MISS to measure Layer-2 holistic pass.
- `/oss:review` → **currently excluded** — skill fetches live GitHub PR via `gh`; synthetic Python input cannot substitute; pipeline generates problems but skill cannot run them; deferred until fixture diff-format mocking added *(skip — even if oss plugin present)*
- `/research:plan` → synthetic optimization goal (e.g. "reduce pytest runtime by 30%"); measure whether plan mode produces complete, valid `program.md` with all required sections, plausible `metric_cmd`, correct `direction`, coherent `scope_files` *(research plugin required — skip if `$RESEARCH_AVAILABLE` empty)*
- `/research:judge` → synthetic `program.md` with N injected plan-quality issues (e.g. missing guard command, absent `direction`, non-existent `scope_files` path, invalid `agent_strategy`); measure whether judge correctly identifies each injected issue at right severity *(research plugin required — skip if `$RESEARCH_AVAILABLE` empty)*
- `/develop:review` → synthetic Python file with N injected code-quality issues (style, correctness, coverage gaps); measure whether review identifies each injected issue at correct severity level *(develop plugin required — skip if `$DEVELOP_AVAILABLE` empty)*
- `/develop:debug` → diagnostic reasoning phase only: synthetic traceback, relevant source snippets and frozen test outcomes with a known root cause and plausible rejected alternatives. Each `task_prompt` requires a diagnosis supported by the supplied evidence, one falsification check and the next owner/action; no test execution, source edits, live probes, subagents or interactive gates. Ground truth = decisive source tokens and evidence-to-cause relationships, not a guessed fix *(develop plugin required — skip if `$DEVELOP_AVAILABLE` empty)*
- `/foundry:investigate` → hypothesis ranking and diagnosis only: synthetic symptom plus frozen environment/config signals and probe outcomes with a known root cause. Each `task_prompt` requires identifying the supported cause, rejecting contradicted alternatives and stating the next action; no commands, environment inspection, source edits, subagents or interactive gates. Ground truth = supplied decisive signals and their causal roles; unresolved fixtures require an explicit inconclusive diagnosis
- `/codemap-py:query-code` → **problem generation must produce an actual synthetic codemap-py index file the target loads and queries through the real CLI/tool** — never inline the graph as prose/code for the target to reason over directly. Inline-data problems collapse to a plain reasoning task both arms solve identically, which flattens every A/B delta to `none` and never exercises the skill's actual capability (index correctness, query latency, tool-call discipline). Domain: synthetic codemap index with known centrality/coupling values; measure whether `central`, `coupled`, `deps`, `rdeps`, `path` queries return correct modules matching ground-truth graph structure *(codemap-py plugin required — skip if `$CODEMAP_AVAILABLE` empty)*
- `/codemap-py:query-code fn-blast` → same problem-generation requirement as above (real index + CLI, not inline data). Domain: synthetic codemap-py index with N modules and known rdeps graph; present developer-framing task ("you are about to modify function X — assess blast radius"); measure recall of expected fn-rdeps callers found in response (≥0.7 recall = correct); ground truth = injected fn_callers list *(codemap-py plugin required — skip if `$CODEMAP_AVAILABLE` empty)*
- `/codemap-py:test-impact` → generate an actual synthetic index and Python project inside the problem's run directory, queried through the real codemap-py CLI; give an explicit module or `module::symbol` target so no input-selection gate is needed. Include direct/transitive test callers or importers, mock-only tests, unrelated tests and `--no-mocks` cases; ground truth = expected impacted test paths and explicit dynamic-dispatch caveats. Measure selected tests and the proposed pytest command; never execute tests or inspect the real project's working-tree changes *(codemap-py plugin required — skip if `$CODEMAP_AVAILABLE` empty)*
- `/codemap-py:scan-codebase` → synthetic Python project with known module structure; measure whether scan correctly identifies modules, dependencies, and produces valid index *(codemap-py plugin required — skip if `$CODEMAP_AVAILABLE` empty)*
- `/codemap-py:rename-refs` → problem generation should exercise the CLI-driven steps (index validation, find-symbol/fn-rdeps queries, the >50-caller budget gate, `git mv` module rename, re-scan verification), not just static text-editing correctness — a problem solvable by direct text substitution alone doesn't test the skill's actual workflow. Domain: synthetic Python project with known symbol/module rename targets and caller graph; measure whether rename correctly updates definition site, import call sites, `__all__` re-exports, and Sphinx refs; ground truth = old symbol absent from post-rename index and all static callers updated *(codemap-py plugin required — skip if `$CODEMAP_AVAILABLE` empty)*
- `/codemap-py:integration` → synthetic project with known skill integration opportunities; measure whether integration correctly scores and ranks candidate skills *(codemap-py plugin required — skip if `$CODEMAP_AVAILABLE` empty)*
- `/research:verify` → paper-vs-code fidelity check; inject N known deviations (hyperparams, architecture, loss function, preprocessing); score recall per dimension (F, H, E, N, C) *(research plugin required — skip if `$RESEARCH_AVAILABLE` empty)*
- `/research:run` → synthetic `program.md` with known metric/guard/config; measure whether run mode correctly sets up iteration loop and applies rollback guard on guard failure; calibrates R0–R3 steps only (full multi-iteration loop excluded — too long-horizon) *(research plugin required — skip if `$RESEARCH_AVAILABLE` empty)*
- `/research:sweep` → synthetic goal string; measure whether sweep correctly auto-plans, passes through judge gate, and hands off to run with correct flags — bounded handoff phase only, sweep's sustained multi-run execution excluded (see Excluded list below); ground truth = presence of plan output file and judge approval/rejection signal *(research plugin required — skip if `$RESEARCH_AVAILABLE` empty)*
- `/research:retro` → synthetic `.experiments/state/*/state.json` + run logs; measure whether retro correctly identifies dead iterations, classifies them, produces structured retrospective report; ground truth = injected iteration outcomes *(research plugin required — skip if `$RESEARCH_AVAILABLE` empty)*
- `/research:fortify` → synthetic ablation plan with known component importance order; measure whether fortify correctly ranks components and identifies reviewer questions; calibrates F1–F3 only (full execution loop excluded) *(research plugin required — skip if `$RESEARCH_AVAILABLE` empty)*
- `/oss:analyse` → `mode: thread` · `haystack: ≥15 candidate items (issues/PRs/discussions with number, state, title, body snippet), ≥3 near_misses sharing title words or the error text but a different root cause` · `template_sections_not_fp: Related` · `sev_label: Priority` · `real_fixtures: benchmarks/calibrate/oss-analyse/real` · `fetch_store: benchmarks/calibrate/oss-analyse/real-fetch` · `open_shape: true` · `verdict_tier: real` — synthetic issue thread at realistic shape (title, body, a few comments, labels; real duplicate threads run 2–5 comments) plus the candidate pool a repository search returns; measure whether thread analysis names the true duplicate (`decisive` = `#N`, role `duplicate`) or states that none exists, rules out near-misses, catches a stale or wrong maintainer claim, and gives an actionable next step. Item type is stated in the fixture, so it is never a ground-truth item *(oss plugin required — skip if `$OSS_AVAILABLE` empty)*
- `/oss:analyse vitality` → `mode: vitality` · `derived_gt: true` · `boundary: true` · `weak_probe: off` — scoring phase only: the fixture is a pre-fetched vitality DATA_FILE (JSONL in the dataset shape `oss:gh-scraper` writes and `bin/vitality_extract.py` reads, realistic volume) inlined as the problem `input`; ground truth per axis = the `band` that the oss plugin's `bin/vitality_extract.py --data-file <fixture> --group A|B|C` prints for it, written into the problem by the pipeline before Phase 1b, never authored by the generator (`decisive` = the band, role = `Axis <n> band`; Phase 1b passes `--derived-gt`, which skips only the token-occurrence check); save each of the three extractor outputs as `derived-<problem_id>-<A|B|C>.json` in the run dir for `--boundary`. High and extreme fixtures put at least 3 axes one step from a different band — a checkpoint axis one checkpoint from a band cutoff, a trajectory axis one sub-signal level from a band line, a 🔴 clause axis held by exactly one red condition, or a 🟡 clause axis one 🟢 clause short (a 🟢 clause axis never counts), and extreme adds one data-quality trap (bot-inflated activity, a partial page, stale timestamps) — difficulty here is band edges, not obscurity, because every band follows from the shipped rubric; measure whether the target reports each axis band and the top risk the bands imply. The target scores inline under the fixture contract (no data fetch, no scorer spawns) *(oss plugin required — skip if `$OSS_AVAILABLE` empty)*
- `/oss:analyse evolution` → `mode: evolution` · `solver_model: sonnet` · `precision_gate: per-role` — adjudication phase (E3) only, the one model step of the mode; scan, scoring and rendering are deterministic and tested elsewhere. The generator writes, per problem, a spec list of 3–8 ambiguous fixes, each `{fix_id, fix_entry, candidates, evidence}` with 2–5 candidate columns in the field shapes the oss plugin's `bin/evolution_scan.py` documents (`fix_entry`: `entry_id`, `kind`, `release`, `text`, `refs`, `commits`, `link_method`; `evidence`: `status`, `blamed`, `context_blamed`, `files`, `symbols`; candidate: `column_id`, `title`, `kind`, `release`, `footprint`, `signals`), saved as `spec-<problem_id>.json` in the run dir; the pipeline renders it with `python <oss bin>/evolution_scan.py render-request --spec <spec> --out <request>` before Phase 1b and inlines that request list verbatim as the problem `input`, so the target sees the production prompt, fences included. Ground truth: one item per repaired column — `decisive` = that `column_id`, role `fix <fix_id>` (a two-column fix carries two items); a fix whose evidence supports no candidate carries one item with `decisive` `none`. Near-misses: a candidate sharing files, symbols or wording with the fix but repaired by nothing in it. Each `--full` set covers the evidence routes the prompt's rules name, at least once each across medium to extreme: a direct link (a `blamed` commit in the correct footprint), an inherited link (`blamed` commits in no footprint, the correct candidate's `signals.method` = `inherited`), an add-only fix (`blamed` empty, a `context_blamed` commit in the correct footprint), and a fix whose `status` is not ok, decided by entry text and symbols. Difficulty: trivial/low — the entry text names the feature; medium — only the blame evidence decides; high — the entry wording points at one candidate while blame and footprint point at the correct other one, or a two-column fix; extreme — adds an unknown-is-correct fix with tempting candidates and, inside one fenced entry text, an instruction steering the verdict to a wrong column, scored only by the verdict staying correct (the verdict schema has no field to report it). Every `task_prompt` states that the request is already rendered, that the target starts at E3 and writes the verdict list only, and that it runs no `scope`, `run` or `ingest` step (the fixture has no store, clone or lock). The target answers as the E3 adjudicator under the fixture contract: one verdict list `[{key, fix_id, verdict}]`, `verdict` = `{"columns": {"<id>": <0..1>}}` or `{"unknown": true}`. Scored per ground-truth item: found when its `column_id` is named in that fix's `columns` (`unknown` for `none`); every named column that no item of that fix carries is a false positive and, through `precision_gate: per-role` (role `fix <fix_id>`), voids the found items of that fix. Calibration bias reads the response's `## Confidence` score as for every domain; per-column confidences are recorded, not scored. The prompt carries its own answer instructions, so the Phase 1c probe tests a weaker model, not the absence of the skill: a hit on high or extreme marks the problem too easy *(oss plugin required — skip if `$OSS_AVAILABLE` empty)*
- `/oss:release` → synthetic git log with N commits of known classification (breaking, feature, fix, internal); measure whether release notes correctly classify each commit and omit internal-only entries; ground truth = injected commit metadata and expected output sections *(oss plugin required — skip if `$OSS_AVAILABLE` empty)*
- `/foundry:distill memory` → synthetic `.notes/lessons.md` corpus with N injected lessons of known disposition (→ rule, → agent update, → skill update, → already covered, → too narrow); measure whether distill correctly classifies each lesson and generates accurate proposals; ground truth = injected dispositions and target files
- `/foundry:manage update` → quoted content-edit directives only, against a uniquely named fixture agent/skill file with an unambiguous type; never rename, create, delete or permission operations. Each `task_prompt` includes the complete quoted directive with spaces so it cannot parse as a bare rename operand. Measure requested content changes and the description-changed flag; ground truth = exact requested fixture edits, unchanged entity name and expected flag
- `/foundry:humanizer` → synthetic human-facing prose seeded with N AI-writing tells of known class (LLM-vocabulary cliché, banned construction, formatting tell — taxonomy from `humanizer`'s own SKILL.md); run the target in `check <file>` read-only mode so scoring reads a findings list, not a rewritten file; recall = injected tells reported; `scope_fp` = flagged spans that were never injected (punishes over-flagging of ordinary human prose); ground truth = the injected tell list with class per span

### Step 2: Spawn skill pipeline subagents

Mark "Calibrate skills" in_progress. **Availability check** (vars set in SKILL.md Step 2): exclude skills marked with plugin requirements above when plugin absent. Log: "<plugin> plugin not installed — skipping <skill> calibration" per excluded skill.

For each skill in domain table (after exclusions), spawn one `general-purpose` pipeline subagent with `model="sonnet"`. **Spawn in batches of `$PIPELINE_BATCH_SIZE` (4 when this category runs alone, 2 while two categories in flight — see constants)**, reduced when SKILL.md's session-wide budget requires it: issue up to that many skill pipeline spawns per response, collect every result in the batch via completion notifications and the SKILL.md Step 2 batch deadline (never a waiting tool), spawn next batch. Skills within a batch run concurrently; batches sequential. Do NOT spawn all skills in one response.

For skill targets (target name starts with `/`): the pipeline template's Phase 2 fixture contract applies — complete SKILL.md, the entry's `mode:` file and everything that mode loads, then the fixture override line. Never frontmatter only. Pipeline template write-and-acknowledge pattern still applies.

`/research:plan` and `/research:judge` are separate skills, not modes: resolve their own SKILL.md via registry first, falling back to source-tree path:

- `/research:plan`: `python "${CLAUDE_PLUGIN_ROOT:-plugins/cc_foundry}/bin/get_plugin_install_path.py" borda-ai-rig research 2>/dev/null` → append `/skills/plan/SKILL.md`; fallback: `$(ls -td ~/.claude/plugins/cache/borda-ai-rig/research/*/skills/plan/SKILL.md 2>/dev/null | head -1)`; skip calibration for this target if fallback returns empty (research plugin not installed)
- `/research:judge`: same helper → append `/skills/judge/SKILL.md`; fallback: `$(ls -td ~/.claude/plugins/cache/borda-ai-rig/research/*/skills/judge/SKILL.md 2>/dev/null | head -1)`; skip calibration for this target if fallback returns empty (research plugin not installed)

Read resolved path (plan wizard steps P-P0–P-P3 for `/research:plan`; steps J1–J6 for `/research:judge`). `<TARGET>` remains the plugin-prefixed skill name (`/research:plan`, `/research:judge`); only `<RUN_SLUG>` uses kebab form (`research-plan`, `research-judge`).

For `/research:judge`, calibration pattern mirrors `/foundry:audit`: inject N specific known issues into synthetic `program.md`, score recall of injected issues against judge's findings list. Ground truth = injected issues and severities (per J2 severity table: critical/high/medium/low).

For `/research:plan`, calibration measures output completeness: generate synthetic goal, score whether produced `program.md` (a) contains all four required sections (Goal, Metric, Guard, Config), (b) has `direction` field, (c) has non-empty `scope_files`, (d) includes plausible `metric_cmd`. Ground truth = checklist; recall = fraction of checklist items present.

Load the pipeline template first — no `~/.claude/skills/` copy exists (setup symlinks only `rules/*.md` and `TEAM_PROTOCOL.md`):

```bash
export CSID="${CLAUDE_CODE_SESSION_ID:-$PPID}"
IFS= read -r LOCAL_MODE < "${TMPDIR:-/tmp}/calibrate-state-${CSID}/local-mode" 2>/dev/null || LOCAL_MODE="false"
python "${CLAUDE_PLUGIN_ROOT:-plugins/cc_foundry}/bin/load_mode.py" calibrate templates pipeline-prompt.md $([ "$LOCAL_MODE" = "true" ] && echo --local)  # timeout: 5000
```

Each subagent receives the pipeline template printed above with substitutions:

- `<TARGET>` = skill name including `/` prefix (e.g., `/foundry:audit`)
- `<DOMAIN>` = domain string from table above for that skill, without its trailing availability note (`*(<plugin> plugin required — skip if ... empty)*`): the orchestrator applies that note before dispatch, and a generator reading it treats it as a reason to skip every problem
- `<N>` = 3 (fast) or 10 (full)
- `<TIMESTAMP>` = current run timestamp
- `<MODE>` = `fast` or `full`
- `<AB_MODE>` = `true` or `false`
- `<LOCAL_MODE>` = `true` or `false` — from `--local` flag; when true pipeline resolves target file from source tree
- `<TARGET>` for a mode-level entry stays the skill (`/oss:analyse` for `/oss:analyse vitality`) — it resolves the SKILL.md
- `<TARGET_LABEL>` = the entry's backticked name (e.g. `/oss:analyse vitality`)
- `<RUN_SLUG>` = Step 1's safe conversion: strip the leading `/`, then replace `:`, `/` and spaces with `-` (e.g. `oss-analyse`, `oss-analyse-vitality`); `--apply` always passes it to `resolve_agent_file.py --run-slug`
- `<PROBLEM_SET_VERSION>` = SKILL.md constant `PROBLEM_SET_VERSION`
- `<FLOORS_ARG>` = `--floors high=<H>,extreme=<E>` from the entry's `scale_chars:`, plus `--derived-gt` for `derived_gt: true`, `--open-shape` for `open_shape: true`, `--boundary` for `boundary: true`; else empty
- domain keys (`mode:`, `haystack:`, `template_sections_not_fp:`, `sev_label:`, `real_fixtures:`, `fetch_store:`, `precision_gate:`) are read by the pipeline from `<DOMAIN>` itself

**Partial-calibration principle**: individual phases with deterministic, auditable outputs can be calibrated even when full orchestration cannot. The full `/research:run` loop (requires live metric commands, git state, real guard scripts) is excluded. Bounded phases producing structured, inspectable output are in scope:

- `/research:plan` — config wizard; output is `program.md` checkable against completeness schema
- `/research:judge` — plan auditor; output is findings list checkable against injected known issues (same pattern as `/foundry:audit`)

Only the bounded phases in the domain table are included. Remaining orchestration in `/oss:resolve`, `/foundry:manage`, `/develop:*` and `/research:*` depends on live state, interactive choices or sustained execution; exclusions below identify those boundaries.

Interactive skills excluded — their workflow is driven by `AskUserQuestion` answers, which a calibration pipeline subagent cannot receive, and no deterministic ground truth exists: `/foundry:create` (content outline co-creation), `/foundry:brainstorm` (idea-to-spec co-creation), `/foundry:manage create` (scaffold choices confirmed with the user), and `/foundry:manage update` rename operations (rename confirmation); only quoted content-edit directives are calibrated above.

Run dir per skill: `.reports/calibrate/<TIMESTAMP>/<RUN_SLUG>/` (e.g. `foundry-audit`, `oss-analyse-vitality`)
