# Adversarial Convergence Loop

Use this procedure when independent review produces findings and authorized work fixes them: pre-commit review, review/remediation pairs, root-cause fixes, and report revision. A review-only request does not authorize edits. This is the canonical procedure; other plugins ship generated byte-identical copies so installation never requires a sibling plugin.

## Scope and authority

Before the first review, record the objective, specification, reported symptom, allowed files, implementation author, acceptance checks, and existing workflow/run. Preserve unrelated changes. Unknown failures require root-cause evidence before a fix. The parent owns edits, integration, gates, and acceptance; reviewers return evidence, not permission.

Run at most **3** independent review rounds by default, including the initial review `W_0`. A round consists of review, triage, and any permitted local fixes; those fixes need a later independent review before closure. The last round cannot end with an unreviewed fix presented as clean. This bounded sequence must be planned before dispatch. It is not permission to expand a parallel wave or bypass a caller's stricter reviewer admission, provenance, approval, or retry rules.

Each reviewer receives the specification, symptom, exact current diff, relevant source and acceptance evidence, scope exclusions, and requested checks. Never supply the implementation narrative or fork the implementing agent's conversation. Identify earlier findings by stable signature when asking for verification, retaining original evidence without the implementer's justification. Supply source inline when the reviewer cannot read files; paths alone are not inspectable context. Record actual reviewer identity and coverage. Claimed independence or a ledger field is not proof of runtime provenance.

For state-changing workflows, include the producer, its next consumer, and the next ordinary user action in the review boundary, including relevant unchanged callers. Ask whether the verified postcondition actually establishes the consumer's precondition and whether all local checks could pass while the user's intended result fails. Treat prior design approval and tests asserting the selected operation as insufficient evidence of that end-to-end property. Request a concrete counterexample or outcome-based probe for material assumptions about identity, ownership, destination, lifetime, retry, or resume. Record missing downstream context as a coverage gap; a zero finding score does not establish uninspected workflow safety.

If no permitted independent route is available, stop the independent loop with reason `independence-unavailable`. Accessible parent-owned source inspection may continue within authorization, but it is sequential review without independent coverage. Preserve rejected specialist evidence separately; never relabel it as accepted, substitute parent tests for independent review, or launch another paid/rejected route without the required approval or changed evidence.

Before choosing retry or a different route, record the observed failure class and its evidence. Unknown receipt rejection is not evidence of transient transport failure. Retry only when the owning workflow's retry contract permits that class; otherwise diagnose or use a genuinely different permitted route with its limitations disclosed.

## Review, triage, fix, verify

1. Freeze a complete scoped snapshot before dispatch. Include staged, unstaged, and relevant untracked content, not only committed `HEAD`. Record revision, exact diff SHA-256, source coverage, and excluded paths. Preserve each round's diff and returned report unchanged.
2. Join the independent review before editing. Assign stable finding signatures from affected location and failure mechanism, not incidental wording. Each finding names severity, evidence, affected files, and whether it changes a contract. Reconcile duplicates with traceable evidence; never drop an earlier finding from the ledger.
3. Validate findings against the specification and actual source. A false positive may be `rejected` only with explicit refutation evidence. A patch becomes `fixed-pending-verification`; it still counts open until an independent reviewer verifies the fix on the new snapshot. Tests support that verification but cannot replace it. Carry closed entries forward so regression can reopen the same signature. Do not rename findings or lower severity to manufacture progress.
4. Calculate the score from findings still open at the independently reviewed snapshot, including `fixed-pending-verification`. Apply hard stops before the trend table. On the initial review there is no ratio; if findings remain and no hard stop applies, make only authorized local fixes and use the next round.
5. Fix each valid finding where it sits, with the smallest change that closes it: one predicate, call site, or local implementation. A finding is never permission to restructure its surroundings. Run the relevant regression checks, freeze the changed snapshot, and obtain the next independent review only if no stop condition applies and a round remains.
6. Before acceptance, capture the current snapshot again. It must match the final independently reviewed snapshot. Later edits, formatter changes, target merges, or source updates invalidate a clean claim until reviewed. Complete the caller's ordinary gates, artifact validation, promotion, and final output; a clean loop is not a merge decision or automatic commit authorization.

## Scores and stop rules

Sum weights of open findings once per stable signature:

| security | critical | high | medium | low | nit |
| -- | -- | -- | -- | -- | -- |
| 20 | 10 | 6 | 4 | 2 | 1 |

`W_n` is the score at independent review *n*, with initial `W_0`. `r_n = W_n / W_{n−1}`; do not divide when the previous score is zero because that run is already clean. Severity follows demonstrated impact. Explain disputed assignments; do not inflate stylistic issues or soften security defects for a better score.

Hard stops override score improvement:

- An open or `fixed-pending-verification` structural finding stops the loop immediately; do not apply further changes. Structural means changing a contract: script arguments/output, module boundary, shared schema, skill step order, or any fix reaching files the finding does not name. Report its blast radius and ask for explicit approval as a separately scoped change; never silently apply it inside the loop, even when it is the only finding or `r_n ≤ 0.5`. A separately approved correction run may retain independently `verified-fixed` structural findings as closed evidence; they score zero and do not block that run. Preserve the original stopped ledger; appending a later closure to it never authorizes continuation.
- The same open finding signature in two consecutive reviews stops immediately; do not wait for the cap.
- Any open `security` or `critical` finding forbids declaring done or committing, whatever the trend. It may still receive an authorized local fix when no other stop applies.
- Missing independent coverage, invalid evidence, or a stale final snapshot cannot produce a clean decision.

| Condition | Reading | Action |
| -- | -- | -- |
| `W_n == 0` and current independent coverage is valid | clean | Complete the owning workflow's remaining gates. |
| `r_n ≤ 0.5` | converging | Continue only if rounds remain and no hard stop applies. |
| `0.5 < r_n < 1.0` | plateau | Stop this approach; ask for the next scoped decision. |
| `r_n ≥ 1.0` | non-converging | Stop immediately; another unchanged attempt is not justified. |
| Round limit reached with findings open | round-cap | Stop; disclose remaining findings and request direction. |

Stopping on a plateau is a valid process outcome, not successful remediation and not proof that the task is permanently impossible. Preserve the score series and stopped ledger. Further work needs the specific missing decision or materially changed scope/evidence; a new invocation alone never resets recurrence or bypasses a stop.

## Evidence ledger

Keep `loop-ledger.json` and `loop-report.md` in the owning run. The ledger records observed facts; a checker establishes structural consistency, not reviewer authenticity or source correctness.

Schema version `1` uses these fields:

- Root: `schema_version`, `implementation_author`, `current_snapshot`, `rounds`.
- Snapshot: nonempty `revision`, lowercase 64-hex `diff_digest` of exact retained snapshot bytes.
- Round: one-based `index` (1–3; score labels start at `W_0`), `reviewer`, `snapshot`, `report_path`, `findings`.
- Reviewer: nonempty `identity`, boolean `independent`. The identity differs from the implementation author; record effective host provenance in the report, including unavailable verification. An empty rounds list records unavailable independent review, never a clean review.
- Finding: stable `signature`, `tier`, boolean `structural`, `disposition`, and list of nonempty `evidence` strings. Dispositions are `open`, `fixed-pending-verification`, `verified-fixed`, or `rejected`; the latter two require closure/refutation evidence. Carry every prior signature, tier, and structural classification into later rounds. Reopened findings retain their signature.

Each report includes inspected snapshot and coverage, reviewer route/provenance limits, original findings, refutations, verification evidence, and any missing inputs. Retain `round-<index>.diff` and `current.diff` for digest checks; report paths resolve inside the run. An unchanged snapshot digest does not prove independence. A changed snapshot invalidates prior closure evidence relevant to that change.

## Handoff and recovery

Start with the topic and outcome: for example, “The parser review stopped because the same boundary defect remained in two independent rounds.” Never begin with an unexplained “both,” “that,” “blocked,” or internal error code. State each fact once; do not repeat the entire conversation.

For every stop with open findings, report score series (`W_0 → W_1 → W_2`), per-tier counts, each remaining finding's disposition and reason, evidence, owner, and next action. Distinguish code changes from evidence-only closure and target integration. Passing gates does not close findings; zero implemented fixes must be explicit.

Show only completed-round scores: a first-round stop has just `W_0`, a second-round stop has `W_0 → W_1`. The three-label series is an example, not a requirement to invent rounds. With no independent round, show `not-run` and the unavailable reason; do not assign zero, which would imply a clean review.

Explain why the loop stopped in plain English and what can safely continue. Recommend one concrete recovery and name meaningful alternatives. Ask only for the missing decision or authority; never ask the user to repeat approval already given. After an authorized recovery, resume the first unmet checkpoint of the original workflow and finish its normal closing checks. Do not stop merely to tell the user to rerun a command the agent can already execute safely.
