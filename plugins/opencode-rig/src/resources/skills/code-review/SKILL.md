# Code Review

> Read [Evidence rules](../../references/evidence.md). This workflow is read-only with the sole PR preparation exception of one new dedicated local ref and the objects `git fetch` stores; it never writes to GitHub. Follow [Role dispatch](../../references/evidence.md#role-dispatch) for native-agent fallback and stop on reported scope violations; use the shared [Optional command compression](../../references/evidence.md#optional-command-compression) guidance for read-heavy commands.

```bash
git status --porcelain
git diff --stat | tail -n 20
```

## Input

- `workspace` (default): staged and unstaged changes.
- `path <path>`: one file or directory.
- `commit <rev>`: one commit's changed files.
- `pr <number|url>`: optional PR mode when `gh` is authenticated; resolves the PR head to commit mode. Earlier PR commits are a coverage limit unless separately reviewed.
- Optional: an implementation run ID and acceptance criteria for an implementation handoff.

## Workflow

1. **Classify.** `TRIVIAL`, `LOCAL`, `BROAD`, or `HIGH_RISK`, using the scope thresholds in [Rig Plan, Workflow step 1](../rig-plan/SKILL.md#workflow); read those definitions before classifying. Risk categories set depth; they do not grant execution authority.
2. **Start the run.** Prepare the scope before starting:
   - a. For an implementation handoff, first inspect its run with `rig_evidence` (`action: "inspect"`, `run_id: <implementation run ID>`), read its recorded `outputs` and bound plan, and take acceptance criteria from that plan or the supplied criteria. Use only those output paths within the plan's owned scope; exclude unrelated changed paths. If paths or criteria are missing or ambiguous, resolve the scope before starting instead of falling back to every changed path.
   - b. For PR mode, resolve the PR repository and head SHA through authenticated `gh`. Count its commits and resolve its identity and provenance with `gh pr view <n> --json commits,number,url,headRefOid,isCrossRepository,headRepository,headRepositoryOwner --repo <owner/repo>`. Use the PR repository's URL as `<pr-repo-url>` (including for fork PRs), its number as `<n>`, and the first 12 characters of the observed head SHA as `<sha12>`.
   - c. For PR mode, check `git show-ref --verify --quiet refs/rig-review/pr-<n>-<sha12>`; abort if it exists (exit 0), and proceed only on the absent-ref result (exit 1). Stop on any other error.
   - d. For PR preparation, fetch that head into the new dedicated local ref with `git fetch --no-tags --no-write-fetch-head --no-auto-maintenance <pr-repo-url> refs/pull/<n>/head:refs/rig-review/pr-<n>-<sha12>` (no `+`). Stop on failure. Verify with `git rev-parse refs/rig-review/pr-<n>-<sha12>` that the fetched SHA matches the observed PR head; stop on mismatch. Never switch branches or overwrite existing refs.
   - e. For PR mode, inspect `git rev-list --parents -n 1 <verified SHA>`. If the head has more than one parent, stop before starting a commit-mode run and record the limit "PR head is a merge commit; review each parent range separately" in the output; do not start a run with an empty scope. Stop if the parent check fails.
   - f. Start `rig_evidence` with `action: "start"`, `skill: "code-review"`, the exact target paths, and `commit: <verified SHA>` for commit or PR mode; resolve a commit revision to its SHA first. Record the implementation run ID and acceptance criteria with `action: "record"` in `decision`, and the bound plan in `inputs` when supplied.
     - In PR mode, read hosted CI at intake with `gh pr view <n> --repo <owner/repo> --json headRefOid,statusCheckRollup`. For each observation, use `rig_evidence` with `action: "record"` and `decision` to preserve the phase, observed head, check names, states or conclusions, and available job links. Attribute checks only when `headRefOid` matches the verified head SHA. When the read fails, the rollup is empty or `headRefOid` differs from the verified head SHA, use `rig_evidence` with `action: "record"` and `limits: ["PR <n>: hosted CI unavailable at intake for <sha>: <reason>"]`, where `<sha>` is the verified head SHA and `<reason>` names the read error, the empty rollup or the observed head SHA. Continue reviewing immediately, including when checks are pending or failing.
   - g. In PR mode, when the commit count is above 1, use `rig_evidence` with `action: "record"` and `limits: ["PR <n>: only head commit <sha> reviewed; <k> earlier commits unreviewed"]`, where `k = commit count - 1` and `<sha>` is the verified head SHA.
   - h. In PR mode, record the provenance decision before any verification: the PR number, canonical URL and verified head SHA together with `isCrossRepository` and the head repository in `decision`. An unknown provenance is treated as a fork. For a verification, create the host temp root's `opencode/` directory once (it is outside the project, so `mkdir -p` asks once) and a detached worktree at the verified head under it (`os.tmpdir()`, not `/tmp`) in `opencode/review-pr<n>` with `git worktree add --detach`, and remove it with `git worktree remove --force` after verification, including on failure.
3. **Collect exact source.** Record the diff and the complete bytes of every reviewed file. For `workspace`, read the staged and unstaged diffs and current file bytes from the same project root used by `rig_evidence`. Do not use a detached worktree for workspace evidence: it omits uncommitted changes. For commit or PR mode, read the diff and file bytes from the verified commit, not the working tree. For an implementation handoff, compare each output's recorded `sha256` with the new scope entry for that exact path; if an entry is missing or mismatched, stop and report the changed output instead of treating it as the implementation's recorded bytes. A digest change invalidates the review.
4. **Select axes.** `correctness` is mandatory and must be run (cannot be omitted). Add `security` for auth, credentials, deserialization, or network input; `tests` when behavior changes; `api` for public interfaces; `performance`, `docs`, and `data` when the diff warrants. Cap at four axes below `BROAD`. Also ensure coverage records what was actually inspected for correctness.
5. **Dispatch independent reviewers.** Use `rig-auditor` (or `rig_dispatch`). Give each only the task and acceptance criteria, role card, exact source bytes or paths that resolve to those bytes, the diff, their digests, and assigned axis. Reviewers are read-only and return JSON findings; the parent never counts its own reading as reviewer evidence.
6. **Validate findings.** Reject any finding without a concrete file and observed evidence. De-duplicate by signature (file + invariant), not by wording. Use `rig_findings` with `action: "write"`, the axes, the coverage, and `reviewer` naming the independent reviewer(s). That write records the review evidence bound to the scope digest.
   - In PR mode, repeat the intake CI query once at consolidation, record the second observation under the same head check, and report it alongside any change since intake. When the refresh read fails, its rollup is empty or its `headRefOid` differs from the verified head SHA, use `rig_evidence` with `action: "record"` and `limits: ["PR <n>: hosted CI unavailable at consolidation for <sha>: <reason>"]`, where `<reason>` names the read error, the empty rollup or the changed PR head, and identify the intake result as historical. Finish without waiting or polling. Keep hosted check status separate from local verification and from source findings.
7. **Report.** Order by severity. State the axes that ran, the axes that did not, and why. An honest partial review beats a fabricated complete one.
8. **Finalize.** `rig_evidence` with `action: "finalize"`. Open findings are a valid review outcome; they are not a completion failure. Source drift is: start a new review instead of certifying changed bytes.

## Improvement claim evidence

Assess every material improvement claimed in the request, PR title/body or reviewed documentation, including claims without supplied benchmarks. Record each claim, its scope and evidence in the existing review report. Include the relevant claims, supplied evidence and this measurement protocol in reviewer context; the parent reconciles claim dispositions in the final report even when a specialist is omitted. Route performance claims to the performance dimension when admitted by the existing selection rules; the parent retains claim coverage when that dimension is not selected. Preserve existing scope, fan-out limits and execution permissions; inspection-only reviewers hand feasible reproduction checks to the parent. Behavioral claims need targeted tests; correctness tests alone do not prove performance or model-quality gains.

Bind numerical comparisons to exact baseline/candidate revisions, commands, representative workload/data, software, relevant hardware and settings. Attribute supplied results separately from independent reproduction. Use a predefined practical tolerance, appropriate warmup and accelerator timing, repeated measurements, raw samples, sample counts, summary statistic and variability. Check correctness and material tradeoffs. Explain hardware relevance and limit conclusions to measured workloads/devices.

Shared local CPU/GPU, memory pressure or swapping, I/O contention and thermal/power changes can confound measurements. Record relevant observable contention and unavailable observations; never assume isolation. Run comparable baseline/candidate samples sequentially in paired, alternating or randomized order; avoid concurrent competing benchmarks or agent-owned heavy checks. Bound reruns and retain noisy attempts and exclusion criteria. More samples do not remove systematic bias. Never stop unrelated processes or change system resource controls without existing authorization. If noise or unequal contention could explain the effect, label measurements inconclusive and name the quieter or representative-hardware check needed; do not confirm or refute the claim from that run.

Conclude supported, contradicted or unverified per claim, with provenance, tested scope and whether independent reproduction succeeded. Missing hardware or unresolved noise leaves the claim unverified with prerequisite, owner and next check; feasible unperformed checks remain incomplete. Reliable counterevidence is required for contradiction. Missing verification alone is a coverage limit, not a source defect or grounds for rejection. Preserve each workflow's existing readiness and confidence contract.

## Rules

- A fetched PR worktree contains third-party code: running its tests, gate or reproduction executes its configuration, hooks and test code. Read its auto-load surface (`conftest.py`, `pyproject.toml`, `Makefile`, `package.json` scripts, `.pth` files, Git hooks) and the changed files, and report what they contain with an assessed risk (`none`, `borderline`, `high`, `likely-malicious`) — a heuristic, never a safety claim; packages the base already declares and the package index supplies are trusted by name, an added, URL-sourced or lookalike one is reported.
  - A same-repository PR is your own code: run its verification on the host, subject to the hook's trusted-directory rule. A PR head that is not in your history asks once; record `rig_trust` only after the user's literal **Trust this PR** answer.
  - A forked PR under `execution: "fork-sandbox"` (the default) runs verification through `rig_sandbox` with the digest-pinned `sandboxImage`; no host code runs. A verification that fetches dependencies needs `network: true`; state that in the receipt. With no image, the tool asks for `sandboxImage` or the one trust answer. With no container runtime or image, ask the user once per fetched commit to **Trust this PR** and record `rig_trust` only on that literal answer; a declined or unanswered request runs nothing and records the check unverified. `all-sandbox` boxes every verification; `host` asks before any host verification in the fetched worktree.
  - The hook allows a verification outside the project root only for an own worktree at an ancestor commit or a matching per-commit trust record; anything else falls through to the role's shell rule and asks.
- Never write to the repository or GitHub during review. Sole exception: PR preparation may create one new dedicated local ref (and the objects `git fetch` stores); never switch branches, touch the index or working tree, or overwrite existing refs.
- Do not fix findings here; hand them to `code-remediate`.
- A finding must cite source that was actually read; pattern-matched suspicion is labeled as suspicion.
- If an independent reviewer is unavailable, say so and cap confidence; do not substitute the parent's own analysis.

## Output

> Lead with the [handoff table](../../references/handoff.md): verdict, alignment, findings, next action, confidence. Then the evidence below.

For a change review, `Alignment` judges the diff against the repository's current module layout, naming, documentation, test conventions and dependency policy: name the conventions that decided the level and the surfaces that were not checked. A clean diff that contradicts the documented direction is `partial`, and a risky change that follows the established pattern with the risk stated is `high`.

`Verdict` is the source judgment on the [verdict scale](../../references/handoff.md#verdict-scale), taken from the confirmed findings that remain after refuted, stale and already-fixed claims are removed:

- `MINOR_EDITS`: every required correction has bounded impact and a localized remedy, including localized correctness, compatibility, test and documentation repairs. Documentation and missing-test gaps stay here unless a material consequence is shown.
- `MAJOR_REVISION`: a remaining confirmed defect has material impact (a broken supported workflow or binding contract, data or compatibility loss) or needs substantial coupled repair; cite its finding IDs and why a minor correction is insufficient. A fixable critical defect belongs here even when its change is small.
- `INSUFFICIENT_BUT_PROMISING` names the missing implementation and the useful initiative; `REJECT` cites the requirement the scope cannot fit and whether a different scope could.
- For every proven rejection, put `REJECT`, the specific reason and the decisive evidence in the opening `Verdict` cell. Use `FALSE_GOAL` when verified behavior or a binding specification disproves the proposal's stated premise, and `DUPLICATE` when the full proposed outcome already ships. For other reasons, carry through any recorded reason code and explain why the evidence rules out the proposal.
- For a duplicate PR, use `REJECT` only when the evidence covers the entire proposal and the target project already ships its intended behavior. In `Next action`, recommend that the maintainer close the PR as a duplicate, link to the original merged change or resolved upstream issue, and say what it delivered. Identify any relevant remaining difference and explain why it leaves the outcome unchanged. If the proposed difference adds value or unreviewed earlier commits leave it uncertain, judge the reviewed scope on its own evidence.
- Judge the remaining required work against the PR's own purpose and size: a confirmed finding whose required resolution reverses or removes the PR's central change, or rewrites most of its diff, is a direction conflict and never `MINOR_EDITS`. Use `MAJOR_REVISION` when the aim stands and the approach must change, `INSUFFICIENT_BUT_PROMISING` when most of the delivered work must be replaced. Establish it from a binding contract, documented policy or verified callers, never reviewer preference, and name the intent and reworked share in the rationale. A bounded fix to a small part of a large diff stays Minor; line counts alone never establish a conflict.
- Weigh the affected surface, realistic trigger and consequence before repair size. Finding count, severity labels or reviewer votes alone never choose the level, and many minor findings never dilute one dominant finding.
- A missing check, unavailable reviewer or absent hardware is a coverage limit that lowers confidence, never grounds for `INSUFFICIENT_BUT_PROMISING` or `REJECT`. An inspected scope that stays undecidable is `null`, with its prerequisite and next check.

Report run ID, scope digest, axes run and skipped, findings by severity, coverage limits, and confidence.

Reviewer independence is instruction-enforced: the tools accept a reviewer identity string without authenticating its dispatch session. Report the actual independent reviewer and any unavailable review; never present that string as session attestation.
