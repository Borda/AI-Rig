# code-remediate Handoff Supplement

Never use bare `Blocked` or a generic incomplete status as the opening outcome. Both `outcome.title` and `outcome.summary` must name the specific current blocker when remediation is blocked. In the summary, cite current-run gate or unresolved-item evidence and state the next owner/action needed to proceed; do not reuse a stale intake-review outcome or substitute a commit-only blocker for the remediation cause. For example: `Remediation is blocked because the required documentation build could not run; gates.json records the missing dependency. The environment owner must restore that dependency before verification can finish.` Keep this explanation in the existing outcome fields; historical rendering and the separate commit disposition stay unchanged.

Code-remediate has one explicit continuation before promotion and final output: prepare its commit disposition and any eligible plan, render and validate the candidate, then execute its step-12 commit decision. A pending native question keeps commit work pending; a blocked or inapplicable commit still needs an explicit disposition. Refresh the handoff and revalidate after an answer or execution changes that disposition, then promote and emit it. Result validation alone must never skip this continuation.

New code-remediate handoffs additionally require `commit_disposition` with exactly three nonempty string fields: `status`, `reason`, `evidence`. Status is `pending` (choice or authorized execution outstanding), `blocked` (verification/closure/ownership/destination/execution prevents committing), `not-applicable` (no remediation-owned tracked changes), `declined` (explicit matching leave-unstaged answer), or `committed` (all authorized units and post-commit checks finished). Reason explains the actual disposition, next owner/action for blocked work, and remaining unstaged work; evidence points to the existing plan, decision, gate or closure record. Pending and committed require every canonical gate passing or explicitly not applicable, `commit-plan.md`, and an existing evidence file declared as a run-relative POSIX path without symlink components, traversal, or fragments. A passing result requires selected closure except explicitly user-deferred work outside the plan, with consistent deferred counts, user-owned `user-deferred` reason groups, no unresolved local/process/environment/external-owner counts, and local actionable closure complete. A failed result may permit a local commit only after an explicit user request when all selected open obligations are environment-owned verification or independent review owned by an external reviewer or maintainer, all local actionable findings are closed, no canonical gate or critical finding failed, and `commit-plan.md` records `## Explicit Commit Request` and `## Remaining Verification`; result and unresolved item statuses stay failed/open. Each selected open row must retain its intake `item_type` of `review-gate` or `confidence-gap`; an open code, test, documentation, or other finding cannot qualify merely because summary counts label it external. Selected outcome rows must agree with summary counts; only unresolved rows explicitly marked `Deferred: ...` qualify for the passing-result exception, while permitted failed-result rows remain `Blocked: ...`. The workflow owner must verify user authorization, excluded plan paths, actual staged paths, and that the commit message discloses the missing verification or review under `Residual limits:`. Automated checks establish file existence and metadata consistency, not the truth of plan prose, user consent, or Git ownership. Record earlier authorization and created hashes in the plan; a pending disposition never authorizes staging or proves a question was delivered.

The renderer requires this record for every new remediation write and emits it once after verification; candidate validation rejects its omission. Historical `check` and canonical-result reads preserve older records without it. Other skills cannot add it. Explicit caller-contract output retains its exact bytes while the machine handoff still records the disposition. Validation proves structure and gate/result consistency, not the truth of consent or Git ownership; existing workflow preflight and actual control calls remain mandatory.

New review-findings and remediation tables use `layout=concise`. Exact machine columns, row identities, source coverage, detail bindings stay unchanged. Remediation overview: `ID | Severity | Finding | Resolution | Outcome`; resolution expands the exact bound O symbol. Version-3 remediation handoffs require `overview_only=true` on the concise table so chat omits repeated ID detail blocks; an `action-items.md` artifact link is then required because that Markdown resolution ledger retains complete sources and evidence. Older concise handoffs without this field keep their saved rendering. Other skills, PR Snapshot and Review Snapshot don't support concise or grouped layout. Historical grouped/legacy rendering and ID-only blockers stay readable; never retroactively rewrite validated handoffs.

Before remediation scope selection, `final_handoff.py selection` validates `selection.json`, renders `resolution-scope.md`; `--check` verifies exact existing bytes without writes. The inventory contains `schema_version=1`, `presentation_version=3`, `selected_indexes=null` (pending) or a confirmed numeric list, and ordered items with `input_item_id`, `item_name`, `severity`, `selectable`, `summary`, `closure_evidence`, full sources. Selectable items also require `resolution_proposal`. The overview includes a short proposal and derived source-kind counts (`report ×1; online ×2`); full pointers appear once below. Repeated report views belong in source `related_mentions`, with `finding_id` when known — not independent sources. Duplicate item/source/canonical-finding identities or incorrect declared counts fail before any prompt. Record matching `resolution_scope.presentation_version=3`; final validation binds confirmed selection and source inventory to the outcome ledger. Version-2 selection rendering (including omitted inventory version) and legacy artifacts stay readable.

For version-3 remediation outcomes, `resolved_how` starts with a reasoned disposition using exact `<label>: <concrete reason>` syntax. The concise overview displays the reason as Resolution, the label as Outcome; internal status/counts and O/E bindings stay unchanged.

| Internal `resolution_status` | Allowed visible label |
| -- | -- |
| `implemented` | `Implemented` |
| `resolved`, `already-fixed`, `already-applied` | `Verified without code changes` |
| `rejected` | `Rejected` |
| `not-applicable` | `Not applicable` or `Rejected` |
| `duplicate` | `Duplicate` or `Rejected` |
| `needs-clarification` | `Needs clarification` |
| `unresolved` | `Blocked`, `Deferred`, or `Not selected` |

Deferral and nonselection require the actual user decision, not a substitute for investigating valid selected work. Never label blocked work rejected, or evidence-only closure implemented. Record finding-specific change evidence for implementation, actual closure evidence for verification without edits, concrete owner/action for open work. Zero implementations must be explicit in the opening; target integration and green CI are not review fixes. Passing gates stay separate from whether all selected remediation is complete. Historical grouped/legacy output retains its bytes.

`stale` is not a current remediation triage or resolution status. Outdated anchors and conflict-resolution line changes require reassessing the original concern against current code, never dismissal or automatic conversion to `rejected`. Other dispositions retain their existing evidence requirements. Legacy count keys remain for historical compatibility, must be zero in current results.

Selection items also retain nonempty `item_type`; report-origin `review-gate` and `confidence-gap` types determine gate intake counts. Report identity is the review run: sources under one `pr-<n>/run-<NNN>/` directory share it, including the report root, so separate runs may reuse finding IDs. Other paths default to the full source file path; explicit shared `report_id` is required for verified cross-file aliases there. Shared closure text never establishes finding equivalence. Input/output paths must be distinct; output must not be a symlink.

`code-remediate` rows are value-bound to `metadata.final_resolution_table.items`: cells are exactly `input_item_id`, `severity`, `item_name`, ordered compact `report [<report-file>:<line>]`, `report [<report-json>#<finding-id>]`, or `online [<comment|thread|review-id>]` or `online [<parent-id>#finding-<ordinal>]` pointers, `resolution_status — [O<n>]`, and `[E<n>] — owner/status: owner_status`. Ordered table details bind each `O<n>` to `resolved_how`, each `E<n>` to `evidence`; row IDs, `kind:source_id` values, source evidence, full source records in metadata and expanded ledger items must also match exactly.
