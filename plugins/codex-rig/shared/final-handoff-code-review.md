# code-review Handoff Supplement

New assessed code-review `result.candidate.json` promotion and current schema-3 `result.json` validation require a nonempty reviewer assessment list and exactly one matching attributed snapshot for its scope, including the bound aggregate summary. Schema-2 results and schema-3 results without retained proof remain readable as unverified archives and cannot certify completion or remediation intake.

This is a breaking requirement for newly built non-PR assessed results: they previously promoted with no snapshot table at all and must now carry a `Review Snapshot`. Rejection is `code-review-final-handoff-candidate-attribution-missing`. Current schema-3 candidate and promoted results are gated; historical schema-2 artifacts remain readable.

Wherever a `Review Snapshot` is present, assessed validation binds its rows exactly as it binds `PR Snapshot`: fields `Scope`, `Revision`, `CI`, `Type`, `Suggestion` in that order, and a `Suggestion` matching the canonical recommendation. For current schema-3 non-PR results, `Scope` equals normalized `metadata.scope` (`working-tree`, `path`, or `commit`) and `Revision` is exactly `diff sha256:<digest>` from retained `diff.patch`; validation rehashes the file against `metadata.review_input_sha256`. This identifies reviewed diff bytes, not a target path or commit identity; the collector has no structured coordinate for those values. Mismatches raise the corresponding snapshot field, value, suggestion, or retained-diff errors. The heading is new in this release, so no stored artifact predates the binding. Existing attribution shape, author binding, terminal exceptions and caller-contract rules remain unchanged.

New assessed code reviews add `reviewers` to `PR Snapshot` (or `Review Snapshot` for non-PR scope), copied exactly from `metadata.reviewer_assessments`: ordered `{role, rating, evidence}` records with unique readable participant labels, integer ratings 1–5 and retained assessment pointers. Snapshot `summary` copies `review_decision.summary` and remains aggregate prose above the table. The renderer appends `Reviewers | Role (rating), Role (rating).` and immediately below the table prints `Legend: 1 = Approve · 2 = Minor changes · 3 = Changes required · 4 = Insufficient evidence · 5 = Block / Reject.` Do not add this derived row to machine `rows`. Findings and operational blockers add ordered nonempty `authors` lists, matching reviewer labels and canonical record authors exactly. The renderer inserts `Author` after the ID column without changing existing machine cells or removing any summary, verdict, evidence, confidence or finding content. List all contributors to deduplicated findings. Never fabricate skipped reviewers or average ratings. Historical artifacts without attribution remain readable; terminal unassessed branches keep their no-table rules.

New review-findings and remediation tables use `layout=concise`. Exact machine columns, row identities, source coverage, detail bindings stay unchanged. Attributed review overview: `ID | Author | Finding | Resolution proposal | Status`; historical unattributed overview: `ID | Finding | Resolution proposal | Status`; required_change supplies a short concrete proposal. Review ID-only detail groups add context, full evidence, closure criteria, or next actions without repeating finding titles, proposals/resolutions, or status. Finding names the problem; Context explains its mechanism, not a second Issue field. Review rows carry their canonical `title`, `summary`, `closure_evidence`; shared validator binds these and action/evidence cells to the enriched review record. Operational blockers carry canonical `id`, descriptive `title`, `required_change`, `evidence`, and omit summary/closure. Other skills, PR Snapshot and Review Snapshot don't support concise or grouped layout. Historical grouped/legacy rendering and ID-only blockers stay readable; never retroactively rewrite validated handoffs.

New `code-review` unavailable results occur before PR verification: every canonical PR gate must be `not-applicable` with a nonempty reason, and the versioned handoff mirrors those records as checks not run. A successful diagnostic command is not a passing PR check; retain recovery diagnostics separately. Generic gate execution retains normal exit-code semantics. Historical schema-v1 results and presentation-v1 rendered bytes keep their compatibility contract; new results can't use that path to bypass applicability validation.

For v2 unavailable review, bind `outcome.summary` to the actual `metadata.collection_failure.code` and listed safe diagnostic artifacts. It begins with a bounded plain-English stage explanation, then `Reason: <code>`, then only present safe command, checkout, or worktree-preflight diagnostics. When no safe collector reason exists, state once that a more specific cause was not retained; never make that statement when a safe reason is present. Known collection labels use the static stage map; unknown label uses `Source collection stopped before I could verify which PR revision to review.` `local-pr-checkout` says checkout did not complete; `checkout-paths` says local files could not be compared. Never infer checkout failure from missing evidence. `pr-error.txt` is always listed; `command-failure.json`, `checkout-state.json`, `worktree-preflight.json` are listed only when present and validated. A preflight may expose only validated current and expected head identifiers, never its path lists. The single `remaining`/`next_steps` record has an arbitrary stable row ID, `owner=code-review`, the exact failure code in `item`, nonempty recovery action containing the classified operation token plus exact resume condition `Resume only after a fresh collector run produces and validates the PR source bundle.` This permits richer evidence-backed recovery or protected-state decision while rejecting generic repair-only and unrelated CI actions. An unavailable run must not contain `local-checkout.json`.

An assessed `code-review` may use `PR Snapshot` with `Field | Value` and `Review Findings and Merge Blocks` with `Finding / area | Required change | Evidence | Status`. PR scope requires the snapshot; nonzero findings require the findings table.
