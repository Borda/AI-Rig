# Final Handoff Contract

The post-gate presentation checkpoint makes the workflow's final user-facing structure executable. Artifact workflows must write `<run-directory>/final-handoff.json`, render it with `python PLUGIN_ROOT/shared/final_handoff.py render --handoff <run-directory>/final-handoff.json --out-final <run-directory>/final.md --out-validation <run-directory>/final-handoff.validation.json`, bind returned digests under `result.metadata.final_handoff`, pass all skill-specific and shared artifact validators, promote the candidate, then emit validated `final.md` bytes verbatim. Never manually reconstruct or summarize the response after validation.

Rendered section and table labels use portable Markdown bold text such as `**Outcome**` and `**Verification**`. Never emit ATX/Setext headings, ANSI color escapes, or renderer-specific HTML styling; final reports must stay compact and readable in monochrome terminals, saved Markdown, plain logs.

This is a post-gate checkpoint, not a sixth quality gate. Order is fixed: five gates; final-handoff creation and rendering; schema-v2 result candidate; skill validator; shared validator including `final_handoff.py check`; candidate promotion; verbatim final output. A failure in the checkpoint blocks promotion and completion.

Code-remediate has one explicit continuation before promotion and final output: prepare its commit disposition and any eligible plan, render and validate the candidate, then execute its step-12 commit decision. A pending native question keeps commit work pending; a blocked or inapplicable commit still needs an explicit disposition. Refresh the handoff and revalidate after an answer or execution changes that disposition, then promote and emit it. Result validation alone must never skip this continuation.

## Schema

New assessed code-review `result.candidate.json` promotion requires a nonempty reviewer assessment list and exactly one matching attributed snapshot for its scope, including the bound aggregate summary. Shared validation applies this presence gate only to candidates; historical `result.json` intake stays compatible.

This is a breaking requirement for non-PR assessed candidates: they previously promoted with no snapshot table at all and must now carry a `Review Snapshot`. Rejection is `code-review-final-handoff-candidate-attribution-missing`. Stored artifacts are unaffected — only promotion of a newly built candidate is gated.

Wherever a `Review Snapshot` is present, assessed validation binds its rows exactly as it binds `PR Snapshot`: fields `Scope`, `Revision`, `CI`, `Type`, `Suggestion` in that order, and a `Suggestion` matching the canonical recommendation. Mismatches raise `code-review-final-handoff-review-snapshot-fields-mismatch` and `code-review-final-handoff-review-snapshot-suggestion-mismatch`. The heading is new in this release, so no stored artifact predates the binding. Existing attribution shape, author binding, terminal exceptions and caller-contract rules remain unchanged.

New assessed code reviews add `reviewers` to `PR Snapshot` (or `Review Snapshot` for non-PR scope), copied exactly from `metadata.reviewer_assessments`: ordered `{role, rating, evidence}` records with unique readable participant labels, integer ratings 1–5 and retained assessment pointers. Snapshot `summary` copies `review_decision.summary` and remains aggregate prose above the table. The renderer appends `Reviewers | Role (rating), Role (rating).` and immediately below the table prints `Legend: 1 = Approve · 2 = Minor changes · 3 = Changes required · 4 = Insufficient evidence · 5 = Block / Reject.` Do not add this derived row to machine `rows`. Findings and operational blockers add ordered nonempty `authors` lists, matching reviewer labels and canonical record authors exactly. The renderer inserts `Author` after the ID column without changing existing machine cells or removing any summary, verdict, evidence, confidence or finding content. List all contributors to deduplicated findings. Label parent substitutes; never fabricate skipped reviewers or average ratings. Historical artifacts without attribution remain readable; terminal unassessed branches keep their no-table rules.

New code-remediate handoffs additionally require `commit_disposition` with exactly three nonempty string fields: `status`, `reason`, `evidence`. Status is `pending` (choice or authorized execution outstanding), `blocked` (verification/closure/ownership/destination/execution prevents committing), `not-applicable` (no remediation-owned tracked changes), `declined` (explicit matching leave-unstaged answer), or `committed` (all authorized units and post-commit checks finished). Reason explains the actual disposition, next owner/action for blocked work, and remaining unstaged work; evidence points to the existing plan, decision, gate or closure record. Pending and committed require a passing result and every relevant gate passing or explicitly not applicable. They also require `commit-plan.md` and an existing evidence file declared as a run-relative POSIX path without symlink components, traversal, or fragments. Required unresolved closure blocks committing even if executed checks pass. Explicitly user-deferred work outside the plan is nonblocking only with consistent deferred counts, user-owned `user-deferred` reason groups, no unresolved local/process/environment/external-owner counts, and local actionable closure complete. Selected outcome rows must agree with summary counts; only unresolved rows explicitly marked `Deferred: ...` may use this exception, never `Blocked:` or `needs-clarification`. The workflow owner must verify the matching user deferment, excluded plan paths, and actual staged paths. Automated checks establish file existence and metadata consistency, not the truth of plan prose, user consent, or Git ownership. Record earlier authorization and created hashes in the plan; a pending disposition never authorizes staging or proves a question was delivered.

The renderer requires this record for every new remediation write and emits it once after verification; candidate validation rejects its omission. Historical `check` and canonical-result reads preserve older records without it. Other skills cannot add it. Explicit caller-contract output retains its exact bytes while the machine handoff still records the disposition. Validation proves structure and gate/result consistency, not the truth of consent or Git ownership; existing workflow preflight and actual control calls remain mandatory.

`final-handoff.json` has exactly these top-level fields: `schema_version`, `skill`, `branch`, `outcome`, `tables`, `source_records`, `source_coverage`, `verification`, `remaining`, `next_steps`, `confidence`, `artifacts`, `caller_contract`. Schema version is `1`. The helper's executable validation is authoritative for nested types, closed vocabularies, exact columns, row/source uniqueness, completeness counts, confidence bands, closure evidence, branch-specific table rules.

`presentation_version=2` changes only rendered presentation; new workflow handoffs must set it. Omitting it is the historical v1 compatibility path, retaining saved validation, bytes, digest bindings exactly. V2 starts with plain-English outcome prose before technical details or labels, omits an empty Results section, renders one concise checks-not-run line when all gates are not applicable, renders each recovery action once with its owner. The complete machine `outcome`, `verification`, `remaining`, `next_steps` records stay unchanged. Exact caller-contract output stays exact.

Normal artifact workflows use `branch=standard`; `code-review` uses `assessed`, `unavailable`, or `closed`. An explicitly requested exact caller output uses `caller-contract`, records requested format and evidence, forbids normal tables, emits only `caller_contract.output`. Never infer this override merely because concise output would be convenient.

New review-findings and remediation tables use `layout=concise`. Exact machine columns, row identities, source coverage, detail bindings stay unchanged. Attributed review overview: `ID | Author | Finding | Resolution proposal | Status`; historical unattributed overview: `ID | Finding | Resolution proposal | Status`; required_change supplies a short concrete proposal. Remediation overview: `ID | Severity | Finding | Resolution | Outcome`; resolution expands the exact bound O symbol. ID-only detail groups add context, full evidence, closure criteria, or next actions without repeating finding titles, proposals/resolutions, or status. Finding names the problem; Context explains its mechanism, not a second Issue field. Review rows carry their canonical `title`, `summary`, `closure_evidence`; shared validator binds these and action/evidence cells to the enriched review record. Operational blockers carry canonical `id`, descriptive `title`, `required_change`, `evidence`, and omit summary/closure. Other skills, PR Snapshot and Review Snapshot don't support concise or grouped layout. Historical grouped/legacy rendering and ID-only blockers stay readable; never retroactively rewrite validated handoffs.

Before remediation scope selection, `final_handoff.py selection` validates `selection.json`, renders `resolution-scope.md`; `--check` verifies exact existing bytes without writes. The inventory contains `schema_version=1`, `presentation_version=3`, `selected_indexes=null` (pending) or a confirmed numeric list, and ordered items with `input_item_id`, `item_name`, `severity`, `selectable`, `summary`, `closure_evidence`, full sources. Selectable items also require `resolution_proposal`. The overview includes a short proposal and derived source-kind counts (`report ×1; online ×2`); full pointers appear once below. Repeated report views belong in source `related_mentions`, with `finding_id` when known — not independent sources. Duplicate item/source/canonical-finding identities or incorrect declared counts fail before any prompt. Record matching `resolution_scope.presentation_version=3`; final validation binds confirmed selection and source inventory to the outcome ledger. Version-2 selection rendering (including omitted inventory version) and legacy artifacts stay readable.

For version-3 remediation outcomes, `resolved_how` starts with a reasoned disposition using exact `<label>: <concrete reason>` syntax. The concise overview displays the reason as Resolution, the label as Outcome; internal status/counts and O/E bindings stay unchanged.

| Internal `resolution_status` | Allowed visible label |
| -- | -- |
| `implemented` | `Implemented` |
| `resolved`, `already-fixed`, `already-applied` | `Verified without code changes` |
| `rejected` | `Rejected` |
| `not-applicable` | `Not applicable` or `Rejected` |
| `duplicate` | `Duplicate` or `Rejected` |
| `needs-clarification` | `Needs clarification` |
| `unresolved` | `Blocked`, `Deferred`, or `Not selected` |

Deferral and nonselection require the actual user decision, not a substitute for investigating valid selected work. Never label blocked work rejected, or evidence-only closure implemented. Record finding-specific change evidence for implementation, actual closure evidence for verification without edits, concrete owner/action for open work. Zero implementations must be explicit in the opening; target integration and green CI are not review fixes. Passing gates stay separate from whether all selected remediation is complete. Historical grouped/legacy output retains its bytes.

`stale` is not a current remediation triage or resolution status. Outdated anchors and conflict-resolution line changes require reassessing the original concern against current code, never dismissal or automatic conversion to `rejected`. Other dispositions retain their existing evidence requirements. Legacy count keys remain for historical compatibility, must be zero in current results.

Selection items also retain nonempty `item_type`; report-origin `review-gate` and `confidence-gap` types determine gate intake counts. Report identity defaults to the full source file path; explicit shared `report_id` is required for verified cross-file aliases. Shared closure text never establishes finding equivalence. Input/output paths must be distinct; output must not be a symlink.

For normal table branches, every material finding, decision, changed surface, experiment, recommendation, or source-owned remediation item must have one stable row ID. `source_records` is the complete source ledger; each table row names its represented source IDs; `source_coverage.omitted_source_records_total` must be zero. A table may carry ordered `details` entries with exactly `id` and `text`; every detail ID must be unique, referenced as `[<id>]` by cell in that table, with the renderer placing definitions immediately below the table. Remaining work names the related row ID, item, owner, next action; `next_steps` contains exactly the remaining row IDs. Terminal `code-review` branches contain no tables or source records.

`verification` preserves all five gate records in canonical order, uses the corresponding gate `stdout` artifact path as evidence. `confidence.score`, gaps, gap closure status/evidence/rationale, limits must exactly reconcile with the result's confidence metadata. `artifacts` must include the candidate/final result path.

New `code-review` unavailable results occur before PR verification: every canonical PR gate must be `not-applicable` with a nonempty reason, the v2 handoff mirrors those records as checks not run. A successful diagnostic command is not a passing PR check; retain recovery diagnostics separately. Generic gate execution retains normal exit-code semantics. Historical schema-v1 results and presentation-v1 rendered bytes keep their compatibility contract; new results can't use that path to bypass applicability validation.

Every pause follows [Actionable Pauses](native-skill-contract.md#actionable-pauses), including terminal review unavailability and assessed review with a withheld executable check. Use existing fields: `outcome.summary` states the stopped action, concrete cause/evidence, governing rule; the related `remaining` entry names continuing work in `item`, the responsible actor in `owner`, feasible recovery plus exact resume condition in `next_action`. Keep that entry in `next_steps`. For assessed code review, whose outcome is a fixed recommendation, place the complete explanation in the related remaining item and canonical operational blocker when applicable. An exact caller contract must preserve the same explanation within its allowed output. Never reduce handoff to an error code, generic approval request, or instruction to retry unchanged after deterministic failure.

Use the existing `next_action` text for recommended recovery, pending decision identity, consequences, resume condition. When a decision is needed, follow [User Questions](native-skill-contract.md#user-questions): show required context first, then let one native control own the live question and choices; only the plain-chat fallback includes them in `next_action`. Keep the exact original question, accepted answers, scope binding, actual response in existing durable workflow notes without extending closed schemas. Never duplicate a native question in rendered final Markdown. Distinguish continuing work from work paused until a specific condition; never imply a temporary process failure permanently blocks the goal. Keep canonical branch wording, schemas, evidence bindings, historical bytes unchanged. An unvalidated process pause follows the same guidance without claiming a validated final handoff.

For v2 unavailable review, bind `outcome.summary` to the actual `metadata.collection_failure.code` and listed safe diagnostic artifacts. It begins with a bounded plain-English stage explanation, then `Reason: <code>`, then only present safe command, checkout, or worktree-preflight diagnostics. When no safe collector reason exists, state once that a more specific cause was not retained; never make that statement when a safe reason is present. Known collection labels use the static stage map; unknown label uses `Source collection stopped before I could verify which PR revision to review.` `local-pr-checkout` says checkout did not complete; `checkout-paths` says local files could not be compared. Never infer checkout failure from missing evidence. `pr-error.txt` is always listed; `command-failure.json`, `checkout-state.json`, `worktree-preflight.json` are listed only when present and validated. A preflight may expose only validated current and expected head identifiers, never its path lists. The single `remaining`/`next_steps` record has an arbitrary stable row ID, `owner=code-review`, the exact failure code in `item`, nonempty recovery action containing the classified operation token plus exact resume condition `Resume only after a fresh collector run produces and validates the PR source bundle.` This permits richer evidence-backed recovery or protected-state decision while rejecting generic repair-only and unrelated CI actions. An unavailable run must not contain `local-checkout.json`.

## Result compatibility

`write-result.py` creates schema-v2 results, requires `metadata.final_handoff` with schema version, three sibling paths, two SHA-256 digests, branch. `validate-artifacts.py` checks those paths, exact rendered bytes, digests, gates, confidence, result artifact reference, workflow-specific reconciliation. Historical results with no `schema_version` are read as schema v1, remain valid without final-handoff artifacts; new results can't opt into that compatibility path because the writer always emits schema v2.

## Transport limit and manager exception

The checkpoint proves the complete response bytes the workflow must emit, but the current host has no post-send transcript hook that can prove chat transport reproduced them. Treat any later manual rewrite as a contract violation; a future host transcript hook may close this residual transport gap without changing artifact schema.

`agent-shims` remains a documented lifecycle exception because it has no canonical `.reports` result artifact, is excluded from the artifact/calibration roster. Its final chat contract remains advisory until that manager gains a canonical run/result lifecycle; never claim executable final-response validation for it.
