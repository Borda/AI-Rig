# Isolated App Server reviewers

Use only after the user explicitly approves this local host integration and its bounded paid reviewer wave. This route addresses a native launcher that cannot establish mandatory reviewer controls. It does not change the native route, promote sibling consumers, enable write remediation, or weaken required independence. App Server is an experimental host interface: unsupported controls fail closed, and a successful test certifies only the observed candidate/runtime.

## Boundary

The parent owns the launcher, frozen plan, returned text, evidence files, final verdict, and canonical gates. Independent ephemeral App Server threads inspect non-sensitive context under observed read-only/never controls. The adapter disables configured MCP servers and other external capabilities for its invocation; an empty MCP table alone does not disable inherited entries. No installed configuration or authentication store is edited. Existing CLI authentication remains opaque. Missing CLI/authentication is a user-owned prerequisite, never a reason to install or inspect credentials.

Evidence is `app-server-parent-observed`: observations collected directly by the owning adapter, not native collaboration lineage or cryptographic host attestation. The parent correlation ID is not a claim that App Server threads descend from that native thread. Filesystem credential isolation remains `unverified`; read-only does not imply secrets are unreadable. Never supply sensitive contexts or market this route as hostile-child isolation. An accepted artifact validates retained observations and bindings, not their resistance to a hostile parent rewriting all evidence.

## Freeze and execute

1. Complete normal risk routing and primary review first. Freeze one to four unique canonical Terra/Luna roles; Sol roles are unsupported by this adapter. Required QA/challenger cannot be replaced by parent substitutes.
2. Create one context per role, beginning with the full exact installed `roles/<role>/ROLE.md` bytes, followed by narrow task evidence, questions, output contract, and stop rule. Reviewers return findings only; write-producing probes stay parent-owned under the shared probe policy. Hash context bytes after completion.
3. Write a schema-1 JSON plan with `consumer_id="code-review"`, `task_sensitivity="non-sensitive"`, `review_run_id`, `parent_thread_id`, exact `review_input_sha256` for the run's `diff.patch`, absolute existing `cwd`, and `nodes`. Each node contains `role_id`, canonical `model`, `reasoning_effort`, `role_card_sha256`, relative `context_path` beneath the plan directory, and `context_sha256`. Freeze the plan before launching; never repair it retroactively.
4. Inspect `python PLUGIN_ROOT/shared/app_server_review.py --help`. First run `python PLUGIN_ROOT/shared/app_server_review.py --plan <plan.json> --check-host`: this checks effective host controls without starting a model turn and does not count as a completed review. After that succeeds, execute the explicitly approved wave with `python PLUGIN_ROOT/shared/app_server_review.py --plan <plan.json> --out <new-output-directory>`. Each owning command uses the host's external-execution approval boundary and required action/capability/credential/filesystem/retry brief. Place the plan directly in the review run; the adapter requires a new output directory beneath the resolved plan directory, rejecting existing symlink escapes before creation. Do not call `thread/shellCommand`, unsandboxed filesystem/process APIs, or another launcher as a silent fallback.
5. The adapter checks controls before turns, dispatches the bounded wave, joins terminal outputs, and proves owned-process cleanup. After output setup succeeds, a failure attempts diagnostic persistence and retains completed output but cannot promote a successful wave. Input validation or unavailable output storage may leave no artifact; report the returned error without claiming evidence exists. No automatic second paid wave: stop and request new scope/approval when another independent pass is required.

## Bind the result

After successful adapter completion, write `specialist-manifest.json` with `schema_version=4`, the normal review identity and triggered-pass fields, and `app_server_execution` containing exactly `plan_path`, `evidence_path`, and `evidence_sha256`. Paths resolve beneath the review run; the evidence digest binds the adapter's `evidence.json`.

Each isolated pass uses `mode="app-server"`, canonical `role_card_sha256`, ordinary `role`, `axis`, `trigger`, `confidence`, and `blocking_findings`, plus the exact adapter-produced `output_path`. Do not populate native `attempts`, `selected_attempt`, or `runtime_execution`. Any optional parent substitute remains `mode="substituted"` and cannot satisfy mandatory independence. Copy the pass records into result metadata as for native reviews.

Run the existing review manifest preflight. It validates adapter evidence, role/card/context/output bindings, current input identity, effective controls, unique completed threads, and cleanup. Mirror its runtime classification in `metadata.execution_mode`; use `execution_evidence_level="app-server-parent-observed"` and `write_parallel_eligible=false`. Claim `parallel` only for validated substantive overlap, otherwise `independent-spawned`; two threads alone do not prove parallelism.

Complete unchanged review notes, findings reconciliation, confidence limits, final handoff rendering, candidate validation, promotion, and `find-review-report.py --complete-run`. Adapter success and two output files are not a completed review. Keep the final report lookup as a distinct acceptance check for PR-scoped runs; a local review must not invent PR identity to exercise it.
