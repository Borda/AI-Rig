# Report compatibility and recovery

Apply this assessment when a requested existing report fails lookup, validation or its next consumer, including an older result, an unpromoted candidate or a resumed remediation inventory. A version number selects a reader and its semantics; it is not evidence that the analysis must be repeated. Distinguish a presentation/consumer mismatch from missing source, provenance, coverage or verification. Record the exact diagnostic, usable evidence, missing proof and smallest feasible recovery in the owning run notes before asking the user.

- Validate supported historical representations under their original contract. Preserve exact source reports, reviewer outputs, role cards, receipts, judgments and attempt history. Never change a schema or presentation marker merely to pass admission, invent provenance, reinterpret historical verdict values as current values, or claim old checks cover changed source.
- Automatically repair deterministic derived presentation or bookkeeping when retained authentic evidence proves every required value. Remediation owns its inventory and rendered scope; Code Review owns its candidate, manifest derivations and finalization. Invoke the owning workflow at its first unmet checkpoint without a new permission question or a model rerun for cosmetics. Retain byte-exact pre-repair artifacts in the run's recovery evidence before regenerating derived files. For historical completed results, preserve the original report before writing a separate candidate; only normal successful validation and promotion may replace the canonical result. Never rewrite frozen dispatch, contexts, source receipts or raw reviewer output. Actual denied capabilities and bounded retry limits still apply.
- A schema-2 archive or another unsupported representation stays unverified while assessed through archive access. Inspect retained source/revision bindings, reviewer outputs, role cards, provenance and gate evidence to identify concrete missing proof; do not stop at its version or feed the archive directly into remediation. Existing valid evidence may support producer recovery only where the current validator can authenticate its original bindings. Never transplant evidence between runs or relabel an old response as a fresh review. If authentic retained evidence is sufficient, regenerate only derived artifacts through the producer and validate a current candidate; otherwise record the precise coverage that needs new work.
- When substantive review work remains, offer `Finish with stated limitations` alongside `Repair existing review and add missing coverage` and `Run fresh code review`, recommending the bounded repair only when its evidence and current producer gates make it feasible. Describe the missing aspects and source drift, if any, so the choice has an objective basis. Repair resumes supported checkpoints and runs only genuinely missing checks or reviewer coverage; it preserves still-valid evidence and all ordinary completion gates. If source drift or unauthenticatable evidence makes bounded repair infeasible, explain which proof must be reacquired and offer fresh review; never promise a partial rerun that the producer cannot validate. Reuse an explicit choice for the unchanged target and gap set. An existing fresh-review choice remains binding.

After automatic or authorized recovery, run both producer artifact validators, normal promotion and `--complete-run`, then the consumer's ordinary admission and preflight. Resume the waiting remediation at its first unmet checkpoint in the same turn; the nested delivery rule applies to recovered reviews as well as fresh ones. A repaired format does not close unresolved findings or missing review evidence. If recovery cannot establish completed-review proof, preserve the exact remaining diagnostic and use the requesting workflow's missing-review decision; safe independent work continues within existing authority.
