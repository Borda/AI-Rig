### Approved inert fixtures

Before native review input is frozen, the parent may admit an inert test fixture occurrence only after verifying it is inert and obtaining explicit user approval. Record each decision in the optional `review-routing.json` `inert_fixture_admissions` list with `input_sha256`, `match_start`, `match_end`, `match_sha256`, `approval_evidence`, and `rationale`. Offsets are Python character offsets; both hashes are lowercase 64-character SHA-256 of UTF-8 bytes for the exact input and matched occurrence. Evidence and rationale must be nonblank and pass strict scanning. Store admission metadata outside untrusted source; frozen plans retain declarations and hashes but do not authenticate human approval. A changed context, new occurrence, or overlapping match requires separate approval. Admission covers native direct, paged/challenge, and batch review input only. Real credentials remain refused; outputs, logs, failure and retry explanations, and portable or isolated runtime contexts remain strictly scanned. Never infer admission from placeholders or paths, or whitelist a pattern. Historical direct-plan versions 1 and 2 remain readable with their original scanning and admission contracts; new direct plans use version 3.

If strict failure-telemetry scanning blocks an in-place retry because an admitted fixture appeared in the original task, preserve the failed evidence and start a fresh review with a neutral task and axis that do not copy the fixture. Rediscover and obtain approval for the new context-bound admissions; re-review any coverage that cannot be reused. This recovery is not guaranteed if later reviewer telemetry also contains the fixture. Never redact or exempt failure telemetry to make a retry pass.

For an opaque sensitive-material rejection, the parent may rerun the same `review_prepare.py prepare` arguments with `--discover-fixtures`. Valid synchronized routing is required; discovery does not change routing, freeze plans, dispatch reviewers, print source text, or return hashes. It returns input IDs and character spans for scanner matches. In version 3, `direct-plan:file:<ordinal>` identifies one complete source snapshot record in canonical plan JSON, and `direct-diff:section:<ordinal>` identifies one complete Git diff section; ordinals start at zero. `direct-plan:remainder:<ordinal>` and `direct-diff:remainder:<ordinal>` cover all remaining bytes. Components retain exact UTF-8 slices and bind the artifact root, artifact path, source root and original byte range. Every version-3 direct input also binds shared non-source review metadata: run and parent identity, reviewer assignments and selections, model choice, brief and role-card digests, independence evidence, comparison scope, actual source revision and verified comparison base (including a base obtained from a PR receipt). Verify that metadata as part of the complete input. Aggregate diff and source-content hashes are excluded from this shared identity; unrelated sibling content is separately scanned and does not enlarge component verification. The complete original aggregate is strictly scanned before partitioning, and any match crossing a component boundary is refused. Historical versions retain aggregate `direct-plan` and `direct-diff` inputs; `direct-task:<role>`, `direct-brief:<role>`, and `direct-role-card:<role>` identify the delivered task, brief and role card. Each run-owned direct input is framed with its class, role when applicable, artifact root and path, and verified source root; its UTF-8 body remains unchanged. Moving the run or changing an input's identity requires a fresh binding and approval. `direct-source:<ordinal>` identifies an individual selected UTF-8 source file, framed with its verified source root and repository-relative path; enumerate the sorted snapshot records before excluding missing or non-UTF-8 entries, and recheck that mapping after any inventory change. `paged:<role>` and `source-context:<role>` identify complete role inputs; `batch:source-NNN:<role>` identifies a generated source fragment. Discovery is local parent-owned work, not an authorization for a reviewer or untrusted source to inspect secrets.

Before exporting any binding, inspect the complete current input by verifying its complete component closure and the deterministic generator: for a version-3 plan file component, its complete source snapshot record, component identity and canonical JSON serialization; for a version-3 diff component, its complete Git section and component identity; for a remainder component, all its original bytes and component identity; for a historical aggregate direct plan, the source snapshot, source and selection metadata, context descriptors, independence evidence, brief references and JSON serialization; for a role input, the role card, brief axis and evidence, all assigned source records, matching diff or untracked notices, and generator transformations. A batch fragment also depends on its role card, prefix, UTF-8 slicing and generated coordinates. Every component is an independent scanner input: verifying one does not attest its siblings or authorize an aggregate fingerprint. Reuse component inspection only when its exact bytes and identity remain current. Comparing scanner matches alone is insufficient: a private-key header can be followed by unknown key material. If any component cannot be verified as safe, do not attest or export that input.

For selected verified inputs, create a parent-owned JSON selection file with `schema_version: 1` and `inputs`: each entry has `input_id`, `complete_input_verified: true`, nonblank `verification_evidence`, and `matches`. Include every scanner match in that input, including overlaps, as `pattern_index`, `match_start`, `match_end`, and `match_sha256`; derive expected match hashes locally from independently known inert material, without printing unknown matches or hashes. Run the same preparation with `--export-fixture-bindings <selection-file>` instead of discovery. The helper checks the current generated input and all expected matches before returning binding proposals; it does not grant admission, authenticate the attestation or consent, or modify routing. Expected-hash equality is a success/failure oracle, so this operation is trusted parent-only. Obtain explicit user approval, add the approved proposals with authentic evidence and rationale to `review-routing.json`, and rerun ordinary preparation. Unselected or changed input remains refused.

Direct-plan matching operates on serialized JSON, so an expected match can include escaped newlines or JSON punctuation beyond the source literal. For a verified source snapshot record, derive expected matches from that complete record encoded with the producer's sorted, indented JSON serialization, rather than hashing a bare source substring. Confirm every derived match against its discovered pattern and span; do not assume the same boundary for other plan components. If the parent cannot verify a match or its complete input safely, leave it unselected and refused.

PR evidence has two tiers.

- Core evidence: `gh pr view` metadata including contributor description/body, authoritative base-repository identity, refreshed target ancestry, exact local PR head, and diff derived with local `git diff <base>...<head>` after SHA verification.
- Supplemental evidence: GraphQL review-thread resolution state and derived diff statistics.

Collector and source boundary:

- The collector delegates remote GitHub state reads to `github_read.py`, which uses `gh` as opaque local credential broker: it never invokes `gh auth`, reads token/keychain state, or writes CLI failure output to artifacts.
- That read-only boundary permits audited view commands, REST GET, and GraphQL query operations; public HTTPS fallback cannot establish private PR evidence.
- A classified core command failure is recorded in `command-failure.json` when diagnostics exist.

#### PR fallback

When `gh pr view` metadata fails, public unauthenticated HTTPS fallback is eligible only when all of these hold:

- The failure is `github-network`, `github-auth`, `github-rate-limit`, or `command-timeout`.
- The checkout target is trusted: canonical PR URL must match a configured GitHub remote; a numeric target is bound to valid GitHub `origin`, or the sole GitHub remote when `origin` is absent.

Ambiguous or unsafe targets, permission failures, not-found failures, and unclassified failures remain fail-closed.

Fallback behavior:

- The review-only fallback normalizes limited PR metadata, then uses verified `refs/pull/<number>/head` ref for detached checkout and derives local diff; it never establishes private PR evidence and is never available to code-remediate.
- `online-review-summary.json` must list unavailable fallback evidence as sorted IDs.
- Raw GitHub CLI stderr is never persisted; terminal diagnostics may include safe `failure_reason` enum alongside non-secret classification metadata.

#### Classify scope

Classify diff; write `<run-directory>/scope.txt`:

- `TRIVIAL`: no public API/config/security/ML behavior touched, \<3 files, \<50 changed lines.
- `LOCAL`: one subsystem or 3-7 files; local context explains behavior.
- `BROAD`: 8+ files, cross-subsystem change, dependency/config change, or unclear ownership.
- `HIGH_RISK`: release, security, auth, credentials, deserialization, data pipeline, ML tensor math, CI/CD, or migration behavior, based on evidence beyond public-API touch alone. The mechanical risk floor also raises a change to `HIGH_RISK` when a changed path names `oauth`, `token`/`tokens`, `secret`/`secrets`, `jwt` or `crypto`, a `Dockerfile`, or a file under `.github/workflows/` or `.github/actions/`, so ordinary lexer or tokenizer modules named `token` accept the larger fan-out.

Risk categories determine review depth and specialist preference; they do not grant execution permission or independently prove sandbox, approval policy, or provenance. Public API compatibility remains normal T1 review axis and may elevate tier when verified breaking, migration, or release evidence requires it.

For `scope=pr`, merge-oriented code review is limited to an `OPEN` PR. `collect_pr.py` can also collect historical evidence for merged or closed PR, including its diff, online discussions, refreshed current target state, and exact checked-out PR head; that raw collector evidence is useful for diagnosis but must not receive merge recommendation or feed code-remediate.

- Core evidence includes `pr.json`, `pr-routing.json`, `remote-selection.json`, `target-branch.json`, `worktree-preflight.json`, `local-checkout.json`, and locally derived `diff.patch`. Online evidence includes comments, reviews, `review-threads.json`, `unresolved-review-threads.json`, and `online-review-summary.json`.
- Selected remote matches base repository from PR URL. Fresh target must equal or descend from PR-recorded base (`expected_base_is_ancestor=true`); advancement is integration context, never PR finding or merge blocker. Genuine divergence fails open-PR collection; historical `target-branch.json` may record it.
- Verify isolated source state independently of HEAD equality: block unresolved index, tracked edits, and untracked source files in the review worktree. Preserve unrelated edits in the invoking worktree and record them only as context; they cannot be treated as reviewed PR source. Repeat source-state checks after worktree creation.
- Review worktree HEAD exactly matches metadata; `pr-routing.json` and `local-checkout.json` include `force_policy` proving no automatic forced checkout. Run tests from the recorded worktree, not from the invoking repository checkout.
- Report the detached review worktree path and verified revision in the handoff. That receipt identifies reviewed source only. For an explicit `+review` caller, return the canonical result through [Nested review delivery](../../../shared/final-handoff-contract.md#nested-review-delivery). The caller owns its separate attached checkout.
- Treat unresolved online threads/comments as candidate findings until triaged valid, duplicate, out-of-scope, or already fixed. Never triage a concern as stale: an outdated anchor or line drift does not prove it gone, so follow it into current code. If GraphQL review-thread collection fails or is incomplete, continue source review with empty normalized thread arrays, `review-threads-error.txt`, `review_threads_status=unavailable`, explicit partial-online-triage notes, and confidence gap `PR review-thread resolution status was unavailable; online review triage may be incomplete.` Never convert that supplemental gap into PR finding or merge blocker by itself.

#### Embedded review findings

Read the complete parent body of each review/comment, including nested `<details>`, suppressed comments, nitpicks, and outside-diff suggestions. Enumerate every nested finding before deduplication; `Comments generated`, inline-thread counts, and a summary verdict do not measure embedded obligations. Use `<parent-id>#finding-<ordinal>` in body order starting at 1 as a local source identity, not a GitHub comment ID. Preserve each exact finding body, code/suggestions, location, and the collected parent evidence path; retain the unsplit parent in `reviews.json` or `comments.json`.

In `Online Review Triage`, record parent IDs, advertised per-section counts when present, every fragment identity, and its individual disposition or owning canonical finding. Reconcile counts before deduplication; unexplained omissions block complete-triage claims and remain explicit confidence gaps. Without advertised counts, inspect the entire body and retain the enumeration. Check each suggestion against current code; the bot's suppressed/duplicate label is not a disposition. Group only independently evidenced same obligations across rounds or bots, preserving all source identities and locations; same file or line alone cannot justify merging. Give distinct obligations separate findings. A summary that merely repeats them is not an additional finding. A changed parent body requires fresh enumeration; do not silently reuse identities from an older snapshot. Keep the complete fragment mapping in the review evidence.

#### Collection failure and conflicts

Commit review retains binary patch payloads in the frozen comparison. Treat Git's line-delimited, C-quoted path inventory as encoded paths: decode it before matching names to source or coverage, including paths with escaped control characters. Changed gitlinks and selected gitlink source fail closed because the snapshot cannot capture nested repository source; retain that limitation rather than claiming complete review.

If `files.txt` and `untracked.txt` are empty with no explicit target, fail before gates. If `scope=pr` and `pr-error.txt` exists, fail with captured reason through the Terminal review-unavailable output gate below and do not begin T1/T2 source review.

**Terminal review-unavailable output gate:** A core T0 PR collection failure is process failure, not review result. When `scope=pr` and `pr-error.txt` exists, read and apply [collection-failure.md](collection-failure.md) before writing any output or retrying the collector; successful collection does not load it. The reference preserves the unavailable-output prose, `result.json` and confidence contract, the all-`not-applicable` check profile, the evidence inspection, and the recovery rules per failure class.

For an existing merge or conflict in the invoking worktree, inspect unmerged paths, `MERGE_HEAD` when present, and current HEAD read-only. Report the observed state in plain English. A review-only run never finishes, aborts, or resolves that merge or asks for merge authorization. Review inspects its own detached worktree, so an invoking-worktree conflict does not block collection or source review: continue through normal completion gates and record the conflict as context, never as a PR finding. If collection itself fails, explain that separate failure and the exact remaining recovery decision.

#### PR close screening

**Terminal close gate (PR only):** After successful T0 collection for an `OPEN` PR and before structural context or T1/T2, screen PR goal, description, authoritative project policy/history, and linked upstream evidence. Establish the independent package-purpose baseline below and complete the blind blueprint or its documented applicability skip before any diff evidence used to support this screen; the pre-diff requirement below also applies here. Then inspect only the diff evidence needed for one conclusive proposal-level close reason. This is disposition decision, not source review. If evidence is inconclusive, continue to T1/T2; never close from suspicion, reviewer preference, contributor identity, AI authorship/style, or merely related change.

Use exactly one close code:

| Code | Conclusive evidence | Insufficient alone |
| -- | -- | -- |
| `FALSE_GOAL` | The stated goal contradicts citable invariant, specification, domain fact, or verified current behavior. | Implementation disagreement, stale wording, or unverified claim. |
| `BREAKING_CONDUCT` | Direct evidence that contribution is intentionally malicious or adversarial by design, such as backdoor, exfiltration, or supply-chain attack. | An accidental security bug, poor code, suspicion, or inferred intent. |
| `WRONG_SCOPE` | A documented roadmap, maintainer decision, ADR, or contribution boundary directly excludes proposed goal. | Size, mixed files, or undocumented preference. |
| `WRONG_PROVENANCE` | A documented license or rights requirement and objective evidence of incompatible or unresolvable provenance conflict. | Fork ownership, code similarity, unknown provenance, or missing CLA/DCO signature that project permits contributor to fix. |
| `DUPLICATE` | A verified merged change or resolved upstream issue already supplies same still-applicable outcome. | A similar title, overlapping files, related open work, or same issue area. |
| `UNADDRESSED_REVERT` | The PR semantically reintroduces reverted change and does not address documented reason for that revert. | File overlap, patch similarity, or revert title alone. |
| `SPAM` | Objective irrelevant, promotional, repeated-submission, or non-substantive evidence shows no bona fide project change. | A small change, missing tests, low quality, or AI-generated content by itself. |
| `ARCHITECTURE_VIOLATION` | The proposal directly contradicts documented current architectural principle. | Style preference, abstraction concern, or reasoning that requires detailed source review. |

A close decision requires `confidence >= 0.90`, two distinct evidence sources, recorded counterevidence/falsification check, and binding to verified current PR head. Public-HTTPS fallback evidence cannot close because its confidence cap is `0.89`. For `WRONG_PROVENANCE`, missing required CLA/DCO signature remains normal blocking item unless documented project policy makes conflict terminal. For `BREAKING_CONDUCT`, accidental security defect remains normal blocking finding; only evidenced by-design harm reaches this gate.

On close, skip structural context, T1, T2, specialist routing, detailed findings, severity classification, and normal recommendation step. Write `review-notes.md` with `Review Decision: close`, source findings `not assessed`, detailed review `skipped`, exact close reason, summary, rationale, evidence, counterevidence checked, and `GitHub mutation: not performed.` Emit `status=pass` for successfully completed workflow, zero findings, `review_status=closed`, and `close_decision={"schema_version": 1, "code": "<CODE>", "advisory_only": true, "head_sha": "<verified PR head>", "summary": "<summary>", "rationale": "<rationale>", "evidence": [{"claim": "<observed fact>", "source": "<artifact, repository path, or authoritative URL>"}], "counterevidence_checked": ["<falsification check>"]}`. Include at least two distinct evidence entries. Omit `review_decision`, recommendations, follow-up, review routing, specialist artifacts, and assessed findings tables; the terminal handoff still renders its compact status table. Run shared gates with detailed-review checks marked not applicable and the `review` gate validating close artifact, then run both artifact validators. This result only advises user to close; never close, comment on, merge, or otherwise mutate GitHub.

### Package-purpose assessment

Start every review, including local, trivial, and non-code changes, with **“Is this desired behavior for this package?”** Judge the proposed outcome against the package's established purpose, supported workflows, and contracts before judging whether its implementation is correct.

- Before reading the diff or changed source, establish a bounded independent baseline from the verified pre-change revision's README, public documentation, relevant contracts and maintainer decisions. Use the collected PR comparison base, frozen commit diff base, or recorded local comparison revision; record the revision and source references. Existing implementation and tests are supporting evidence, not proof that an old bug is desired behavior.
- Treat PR descriptions, linked issue claims, and documentation or tests changed by the contribution as proposals to assess, never as authority to redefine package intent. Verify any claimed maintainer authorization independently of the contribution. A supported evolution or explicit maintainer-approved scope change can be desired; absence from existing code alone is not a defect.
- Record an initial `yes`, `no`, or `unclear` assessment with the intended outcome and baseline evidence. After opening the diff, reconcile the actual behavior and side effects against that baseline, including behavior omitted or misrepresented in the description. For detailed reviews, pass relevant baseline evidence and unresolved questions into reviewer briefs, retain the initial and final assessments in the existing review notes' `Scope` section, and explain the final assessment's effect on the recommendation in `Decision Summary`. For terminal close, retain the assessment and baseline in the existing close rationale and evidence; do not add a normal recommendation or claim detailed source review.
- A concrete mismatch becomes a candidate finding with the violated purpose or contract, trigger and consequence; validate it through the normal finding process. Proving malicious intent is unnecessary to report an undesired behavior. Keep the stronger evidence requirements for terminal `WRONG_SCOPE` and `BREAKING_CONDUCT` closure unchanged.
- Missing or conflicting baseline evidence remains `unclear`, with the missing evidence or maintainer decision named. Continue feasible inspection; never invent intent, infer alignment from green tests, or give unconditional approval while a material desirability question remains unresolved. Ask only for a genuinely missing decision through the existing question workflow.

This assessment is mandatory even when the blind blueprint is skipped. If the diff was already read, use ordering recovery and retain a non-blind assessment rather than claiming retroactive independence.

### 03: T1 primary diff review

Blind blueprint first, when declared tier is not `TRIVIAL` and the change adds behavior or public API (T0 evidence: PR body/title, `files.txt`, `numstat.txt` — not diff content). Before opening `diff.patch` or any changed file at head, read only the independent package-purpose baseline above, PR title/body, linked issue bodies, and `files.txt` names; write `<run-directory>/blind-blueprint.md`: the problem restated in two lines and assessed against that baseline, then your own blueprint-level solution — approach, key data structures/functions, edge cases — one page maximum, no code. Then open `diff.patch` for the axes below. Where diff and blueprint diverge: a divergence with a concrete defect and a required change becomes a canonical finding record; one that a prior decision, constraint, or incident could explain becomes a question to the author under `No-Finding Residual Risks` — never a `Findings` row, whose contract requires `required_change` and a status. Same thread means ordering-only isolation, not context isolation; add `Confidence Gaps` line `Blind blueprint written before diff in the same context; anchoring reduced, not eliminated.` Skip the blueprint for pure refactor, style, docs, dependency, or CI changes and when PR body and issues give no usable problem statement; record the skip reason in `Scope`, never invent a problem statement.

Review axes, in order:

- Desired behavior for the package, using the independent baseline and actual change effects.
- API and behavior regressions.
- Test coverage and edge-case gaps.
- Error handling and logging.
- Project coding principles: changed code follows applicable `AGENTS.md` layers for simplicity, readability, reproducibility, short reusable units without low-value argument-remapping wrappers, guard clauses or early `return`/`yield`/`continue`, project docstring-style detection, concise purpose docstrings, and inline comments only for non-trivial implementation blocks.
- Security, data, ML, CI/CD, or release risks signaled by T0.
- Documentation or migration gaps caused by behavior/API changes.

Blocking defaults guide merge judgment; they are not automatic labels:

| Category | Default | Nuance |
| -- | -- | -- |
| CI red or failing check | blocking | Only major or required-check failure. Note single flaky-looking rerun blip without automatically blocking. |
| Missing test coverage for new or changed logic | blocking | Require coverage proportional to changed contract and regression risk. |
| Accidental security bug | blocking | Evidenced by-design harm is terminal `BREAKING_CONDUCT` at close gate. |
| Breaking API change without deprecation or migration path | blocking | Require project-compatible transition before merge. |
| Missing docs for new or changed public behavior | blocking | Missing CHANGELOG entry alone is not blocking and may be completed through release workflow. |
| Performance regression | contextual | Block unexplained regression against recent releases; do not block when correctness fix necessarily removes invalid prior speed. |
| Merge conflicts | not blocking | Record the observed conflict as checkout context. Continue the detached review. |
| Incomplete implementation | blocking | Includes TODOs in changed paths, missing expected error handling, or unfinished public contract. |
| Missing CLA/DCO signature | blocking only when the project requires it | Verify a CLA/DCO bot check or explicit contribution policy first; without such a requirement it is not applicable. |
