# Missing requested PR review decision

Apply when `mode=pr` and `REQUESTED_REPORT=true` has no eligible completed report, including `+review`, `+report`, report aliases and explicit PR report paths. Missing, incomplete, unavailable, invalid or unpromoted evidence reaches this checkpoint only after compatibility assessment and feasible automatic recovery; closed disposition remains terminal. Ask for the remaining substantive review decision before continuation, even when usable current-online/user findings or preliminary hypotheses exist. A version mismatch or repairable derived artifact alone does not trigger this question. Continuing without a completed report requires explicit user confirmation; existing remediation authorization alone does not supply that decision. Retain requested-report intent and all missing proof. Normal source verification and scope selection still precede edits. A previously selected fresh-review-first route remains binding; never silently override it. Bare PR online-only intake does not ask this question. Current-session `review` and local report intake keep their separate finding-evidence contracts.

Freeze the PR target and retain the exact lookup/admission diagnostic in the run notes. For PR-scoped decisions, include the PR number and canonical URL inside the question itself, using `[PR #<number>](<canonical PR URL>)` or the plain URL when Markdown links are unsupported. Derive both from the frozen target, including missing-report and unavailable-PR decisions; never substitute a nearby report's target or leave the link only in earlier commentary. A retrieval failure preserves the classified diagnostic; it does not establish nonexistence when access may be unavailable. Explain once that the requested completed review is unavailable and that continuing with available findings leaves completed-report proof unavailable. When the compatibility assessment identifies feasible bounded recovery requiring new evidence, follow **User Questions** with `How should we complete review evidence for [PR #<number>](<canonical PR URL>)?` and choices `Repair existing review and add missing coverage (Recommended)`, `Run fresh code review`, and `Continue with available findings`. State exactly which aspects need work and which evidence remains usable. If no report exists or bounded recovery cannot satisfy producer gates, explain the concrete missing proof and use `Run a fresh code review for [PR #<number>](<canonical PR URL>) before remediation?` with choices `Run fresh code review (Recommended)` and `Continue with available findings`. Do not offer an infeasible repair. A native control owns the single question/menu; do not duplicate them in context prose. Plain-chat fallback presents the complete question and choices once. Reuse an unambiguous existing answer bound to this unchanged target and decision. Ask before dispatching additional review; declining or dismissing that optional review permits completion within existing authority with the factual limitation. Preserve any separately required finding selection and do not claim the requested report was obtained.

- **Repair existing review and add missing coverage:** explicitly authorizes the bounded work named by the compatibility assessment. Invoke Code Review recovery at the first unmet checkpoint, retaining authentic still-valid source and reviewer evidence; add the missing checks or coverage under normal producer gates. Preserve the original report and do not substitute a full rerun without authorization. Complete both artifact validators, normal promotion and `--complete-run`; then admit that exact canonical result and resume this same remediation run under the fresh-review return rules below. If the proposed repair proves infeasible, retain the diagnostic and ask only for the changed substantive decision.
- **Yes / Run fresh code review:** explicitly authorizes the normal full `code-review` workflow for this PR, with a fresh-review entry decision. Invoke `../../code-review/SKILL.md` end-to-end under [Nested review delivery](../../../shared/final-handoff-contract.md#nested-review-delivery), retaining this remediation run and the unchanged PR target. Complete source collection, normal reviewer coverage, ordered completion gates, both artifact validators, promotion and `--complete-run`.
  - a. Set `FINDINGS_SOURCE` to that exact returned canonical result path; admit it with `find-review-report.py --result <path>` and the recorded producer thread/rollout coordinates when required. Do not repeat latest-report discovery or the fresh-review question. `--complete-run` completes the review's own validated result even if a newer run exists; `--result` still enforces newest-run eligibility for remediation intake and may reject a concurrently superseded report.
  - b. Then resume this same remediation run, only after an eligible completed result is admitted; continue fresh source collection, normal inventory, remediation scope selection, fixes and closing gates. An admitted report with `status=fail` from quality gates or a nonapproval recommendation still continues to remediation. Review completion does not replace remediation completion. If branch verification fails on return, continue through [Source drift recovery](source-recovery.md#source-drift-recovery); do not end with the child review’s final answer. An admitted report recording `execution_mode="serial-fallback"` or a failed multi-role status is a completed nonapproval report: carry its disclosed coverage limit as a named residual limit in remediation notes and the final handoff, never as independent review coverage, and do not rerun the review for it.
  - c. A failed or incomplete review lifecycle checkpoint keeps remediation at report admission while Code Review applies [Reviewer validation recovery](../../code-review/references/validation-recovery.md) or [GitHub Read Execution](../../../shared/native-skill-contract.md#github-read-execution) at the actual failed checkpoint. Do not ask for a new message merely to resume already-authorized recovery; the retained answer does not reset retry limits or override a runtime denial. Ask only for a genuinely missing decision or capability after permitted recovery is exhausted. Do not silently switch to available findings or treat preliminary checks as a completed report.
  - d. A review that completes but cannot be admitted keeps its terminal status. `closed` (`matching-review-closed-not-remediable`) ends remediation with that close disposition and no edits. `unavailable` or a supersession rejection stops at report admission with the exact diagnostic; then ask once through User Questions with choices `Continue with available findings` (the **No** branch below) and `Stop remediation`. For collection failure, put the target and diagnostic in the question itself: `[PR #<number>](<canonical PR URL>) could not be retrieved (<classified diagnostic>); no source review ran. Continue with available findings, with completed-report proof unavailable, or stop remediation?` Do not describe unavailable artifact closure as a completed review or infer nonexistence from an access failure. For supersession, identify the same linked target and the exact admission rejection without claiming source collection failed. Never rerun the review or repeat the fresh-review question for this unchanged target.
- **No / Continue with available findings:** explicitly authorizes continuing current-online/user findings and eligible preliminary records through the existing source, selection and verification gates. Acknowledge that fresh review was declined and completed-review proof remains unavailable. Retain `requested_report=true`, the diagnostic and preliminary/unavailable admission limits; do not silently clear requested review intent or claim complete report-backed remediation. If no usable finding exists, ask for concrete missing finding evidence next.
- **Declined or dismissed additional review:** skip the optional review, preserve the factual report limitation, and continue already authorized source inspection and selected fixes. Do not carry the request into final actions or ask again. Missing source-finding selection or an explicitly pending required authorization remains a separate decision; silence never authorizes new work.
